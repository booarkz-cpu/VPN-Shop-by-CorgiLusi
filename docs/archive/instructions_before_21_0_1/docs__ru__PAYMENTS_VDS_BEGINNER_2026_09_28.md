# Платежи на двух VDS: пошаговый маршрут для владельца магазина

**Проверено по исходникам 28.09.2026, релиз v20.0.18.** Сейчас штатно открыть реальные платежи **невозможно**: полный E2E v2 отсутствует. Кнопка «Разрешить реальные платежи» выключена, API отклоняет включение с HTTP 409. Даже удачный встроенный тест v1 не меняет этого. Ниже описаны действия, которые можно выполнить сейчас, и отдельный порядок открытия **после реализации и проверки v2**. Не исправляйте флаг в базе вручную.

## Словарь

- **Production** — рабочий сервер и реальные деньги клиентов.
- **Staging** — отдельный сервер для пробных оплат, выдачи и возвратов.
- **VDS** — арендуемый виртуальный сервер. **SSH** — вход в его терминал. **DNS A** — запись, привязывающая доменное имя к IP сервера.
- **Webhook** — запрос от кассы на ваш HTTPS API о событии платежа. Возврат браузера на сайт сам по себе не доказывает оплату.
- **Gate** — серверный допуск к приёму новых реальных платежей.

## A. Подготовка без живых списаний

1. Зарегистрируйте домен и арендуйте **два** VDS Ubuntu 24.04 или Debian 12: минимум 2 vCPU, 4 ГБ RAM, 30 ГБ свободного диска каждый. Запишите IP, SSH пользователя и способ восстановления доступа в панели хостера. Подготовьте отдельные staging бот, Remnawave, PostgreSQL, Redis и домены. Одна база или панель на два контура исключена.
2. В панели DNS создайте A записи `api`, `admin`, `app`, `cabinet`, `support` для production и такие же с суффиксом `.stage` для staging. Например `api.vpn.example.com` и `api.stage.vpn.example.com`. Каждая группа должна указывать на свой IP. Удалите неправильные AAAA. В панели firewall VDS разрешите входящий TCP 80, 443 и используемый SSH порт. Не закрывайте SSH до повторного входа через вторую сессию.
3. Установите production, исполняя [команды инструкции v20.0.18](VDS_PRODUCTION_20_0_18.md) по порядку. В установщике выберите кассу `none`. Выпишите секреты и recovery коды в менеджер паролей. В `/opt/vpn-shop/.env` должны быть `APP_ENV=production`, `PAYMENTS_SANDBOX=false`, `COOKIE_SECURE=true`. Не публикуйте `.env` и вывод команд с секретами.
4. Проверьте production: войдите по SSH и выполните `cd /opt/vpn-shop`, `sudo docker compose --env-file .env config --quiet`, `sudo docker compose ps`, `curl -fsS https://api.vpn.example.com/health/ready` (подставьте свой домен). Нужны работающие контейнеры и `ok: true`. Зайдите в `https://admin.vpn.example.com`, включите MFA, откройте магазин и бота, проверьте тестовый тариф и связь с Remnawave без оплаты. В разделе **Безопасность** должно быть «ВЫКЛ — заблокировано».
5. На **втором** VDS повторите установку со staging доменами, ботом и панелью. Установщик первоначально создаёт `APP_ENV=production`; после установки измените на **staging сервере** через `cd /opt/vpn-shop && sudoedit .env` строки `APP_ENV=staging` и `PAYMENTS_SANDBOX=true`. Убедитесь, что домены/токены относятся только к staging. Затем выполните `sudo docker compose --env-file .env config --quiet`, `sudo docker compose up -d --build` и `curl -fsS https://api.stage.vpn.example.com/health/ready`. Не копируйте production `.env` на staging.
6. На staging заведите отдельного покупателя и тариф с небольшой положительной ценой. Проверьте HTTPS всех staging доменов, открытие Telegram Mini App и тестовую выдачу в staging Remnawave. Сделайте резервную копию и восстановите её на **третьем временном чистом стенде** либо другом изолированном месте. Простого файла backup без пробного восстановления недостаточно.
7. Выберите **одну кассу** и получите из её официального кабинета тестовый режим, разрешённый способ тестовой оплаты, URL API и webhook, порядок возврата. Настройте callback на staging API: `https://api.stage.vpn.example.com/api/webhooks/yookassa` (либо `/platega`, `/rollypay`). Проверьте, что HTTPS сертификат действителен и касса видит endpoint. Тестовые ключи храните отдельно. Не используйте реальные карты в sandbox.

| Касса | Что проверить до выбора для полного E2E |
| --- | --- |
| YooKassa | Тестовый магазин и ключи, события `payment.succeeded`, сверка статуса и IP источников webhook, возврат через тестовый API и подтверждение статуса. |
| Platega | У провайдера подтвердить наличие подходящей тестовой среды и доступные методы. Возврат `/transaction/{id}/cancel` может потребовать ручного решения; ответ на запрос ещё не доказательство возврата. Текущий код возврата требует переработки. |
| RollyPay | Платёж `test:true` использует ключ терминала; опубликованный sandbox **не поддерживает возвраты**. Текущая проверка запрещает одинаковый ключ production и staging. Нужна отдельная подтверждённая схема теста возврата и доработка интеграции; сейчас полный PASS невозможен. |

**Важно:** это подготовка, а не готовый E2E. В v20.0.18 обычный `POST /api/payments/create` для внешней кассы на staging даёт 503. Встроенный `scripts/staging-e2e.sh` вызывает служебный маршрут, опрашивает кассу и не создаёт нормальный заказ, не ждёт webhook и не проверяет выдачу/отзыв. Не трактуйте его `[PASS]` как разрешение продаж.

## B. Как прогнать полный staging E2E после выпуска исправленного v2

Следующий список — **условие для будущего релиза**, а не исполнимая процедура v20.0.18. Разработчик должен сначала реализовать весь [контракт v2](STAGING_E2E_V2_IMPLEMENTATION.md), CI и доступный пользователю checkout на staging, исправить возвраты и обработку chargeback. Устанавливайте **один и тот же проверенный тег** на обоих VDS, сделав backup и сверив версию API. Не заменяйте тег произвольным `main`.

1. В **production админке** откройте настройку staging E2E. Укажите публичный HTTPS API **staging**, отдельную staging Remnawave и её токен, ID staging тарифа, только нужного провайдера и его sandbox credentials. Результат, разрешающий production gate, хранится в **production базе**. Проверьте независимость production ключа кассы и staging ключа, списка доменов и базы. Сохранение этой формы меняет revision и закрывает gate.
2. Запустите проверку из production админки. Зафиксируйте run ID, время начала и revision. Ссылку checkout открывайте как отдельный staging покупатель, оплатите официальным тестовым способом один заказ. Никому не пересылайте полный checkout URL. При неизвестном статусе **не нажимайте оплатить повторно**; сначала сверьте provider ID в кабинете кассы.
3. Сверьте по одному order ID: один внутренний `Payment`, один provider intent, правильная сумма и RUB. Повторите запрос с тем же idempotency key и убедитесь, что второго заказа нет. Проверьте доставленный **подписанный webhook** и повторную проверку статуса через API кассы. Ожидайте `paid` и `fulfillment_status=completed`.
4. Откройте staging Remnawave: по конкретному удалённому ID найдите ровно один доступ тестового покупателя, правильный тариф и срок. Повторите доставку того же события штатным механизмом кассы; число заказов, подписок, операций журнала и доступов не должно вырасти. Неверная подпись, сумма, валюта и чужой order ID должны отклоняться. Проверьте повтор после временного сбоя staging Remnawave.
5. Оформите **настоящий тестовый возврат** штатной кнопкой магазина для этого заказа. Дождитесь подтверждённого статуса возврата у кассы, записи финансового события и отзыва доступа именно у того удалённого пользователя. Повторный возврат не должен списать средства второй раз. Поздний success webhook не должен восстановить доступ. Если провайдер не позволяет испытать refund, этот провайдер не прошёл E2E.
6. Убедитесь, что **сервер сам** выдал `status=passed`, `contract_version=2`, `full_e2e=true` и текущую revision. Сравните commit/tag, провайдера и время завершения: результат должен быть не старше 24 часов. Пройдите весь цикл отдельно по каждой планируемой кассе. Сохраните обезличенные ID, время и результаты; карточные данные, ключи и полные ссылки не сохраняйте в отчёте.

## C. Открытие реальных платежей после полного PASS

**На текущем релизе остановитесь здесь.** Кнопка «Разрешить реальные платежи» намеренно неактивна, а API возвращает 409. Когда новый релиз реализует v2 и каждый пункт B реально пройден:

1. На production проверьте `APP_ENV=production`, `PAYMENTS_SANDBOX=false`, `COOKIE_SECURE=true`, домены, MFA, резервную копию и восстановление, доступность Remnawave, корректный production ключ и webhook каждой включаемой кассы. Не вставляйте sandbox ключ в production checkout. Перед открытием сверяйте кассу и webhook по её официальному кабинету.
2. Убедитесь в админке production, что проверка завершилась полным PASS **для той же revision** и не старше 24 часов. Если менялись ключ, адрес, тариф или другая конфигурация, повторите B. Убедитесь, что все неподдержанные кассы выключены в маршрутизации.
3. Уполномоченный администратор в production разделе **Безопасность** нажимает «Разрешить реальные платежи». В реализованном v2 кнопка должна быть доступна только после PASS; backend дополнительно проверяет допуск. Убедитесь, что экран показывает «ВКЛ — разрешено». Если кнопка неактивна/ответ 409, прекратите и исправьте причину; не правьте БД и фронтенд.
4. Создайте **один** контрольный заказ на минимальную допустимую сумму официальным реальным платёжным средством. Сверьте списание и provider ID в кабинете кассы, подписанный webhook, один `Payment`, одну подписку и один доступ в Remnawave. По утверждённой процедуре оформите возврат, дождитесь подтверждения и отзыва доступа. Убедитесь, что сумма сошлась в финансовом журнале. Только затем объявляйте оплату доступной покупателям.
5. Мониторьте новые заказы, необработанные webhook, очередь выдачи, возвраты, состояние gate, резервные копии и журналы. При расхождении остановите новые платежи кнопкой «Заблокировать», сохраните ID операций и проведите сверку с кассой. Не повторяйте списание и не правьте статусы вручную. Результат staging старше 24 часов или изменение его revision должны закрывать допуск автоматически; проверьте это на тестовом контуре до запуска.

## Где смотреть причины ошибки

`sudo docker compose ps`, `sudo docker compose logs --tail=100 backend worker caddy` на **нужном** VDS; `curl -fsS https://api.<ваш-домен>/health/ready`; в админке статус staging E2E, раздел **Безопасность**, заказ и возврат; в официальном кабинете кассы provider ID и доставка webhook; в staging Remnawave удалённый ID доступа. Если что-то не совпадает, зафиксируйте время UTC и обезличенные ID, проверьте DNS/сертификат/firewall/ключ/версию, затем повторите E2E целиком. Секреты и сырые логи клиента не публикуйте.
