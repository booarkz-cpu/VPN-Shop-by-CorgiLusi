# Проверка каждой платёжной кассы: инструкция для новичка

**Проверено по исходникам `main` 28.09.2026; выпущенная версия — `v20.0.18`.** Эта инструкция помогает владельцу магазина понять, что нажать и какой результат записать для каждой интеграции. Адреса `vpn.example.com` и `stage.vpn.example.com` — примеры: замените их своими. Интерфейсы самих провайдеров могут меняться; ссылки в разделах ниже ведут на их официальные инструкции.

> **Стоп для реальных денег.** Сейчас полный staging E2E v2 не реализован. Кнопка «Разрешить реальные платежи» выключена, сервер отклоняет включение с HTTP 409, а внешний checkout на staging — с HTTP 503. Заполнение ключей и тест v1 не снимают запрет. Не меняйте базу, флаг допуска или код ради обхода. Разделы «подготовка» можно выполнить сейчас; тест обычной внешней покупки и контрольное настоящее списание — только после выпуска исправленной версии, успешного полного E2E v2 и проверки каждой выбранной кассы. [Почему так](PAYMENT_AUDIT_2026_09_28.md).

## 1. Откройте нужный файл перед работой

1. Если сервер ещё не установлен, начните с [установки VDS](VDS_PRODUCTION_20_0_18.md); на вопрос о кассе выберите `none`.
2. Для отдельного тестового сервера выполните [подготовку staging](STAGING_VDS_E2E_OPERATOR_20_0_18.md). Понадобятся отдельные домены, база, бот, тестовая Remnawave и тестовый покупатель. Production и staging не должны пользоваться одной базой и одной VPN-панелью.
3. Для одной только ЮKassa есть инструкция [с подробными названиями экранов](YOOKASSA_CLICKS_BEGINNER.md). Этот файл охватывает **все реализованные платёжные направления** и помогает проверить их по очереди.

**Словарь:** *касса* — компания, которая принимает деньги; *webhook/callback* — уведомление кассы серверу; *provider ID* — номер операции у кассы; *order ID* — номер заказа в магазине; *refund* — возврат денег; *staging* — отдельный испытательный магазин. Возврат браузера после оплаты не подтверждает поступление денег: смотрите статус у кассы и подтверждённый webhook.

## 2. Подготовьте рабочее место — делается один раз

1. На компьютере откройте два окна браузера: в первом админка **staging** `https://admin.stage.vpn.example.com`, во втором кабинет **тестовой** кассы. В каждой вкладке проверьте домен и название тестового окружения. Не перепутайте их с рабочими магазинами.
2. Создайте отдельного staging-покупателя и тариф с небольшой **положительной** ценой в валюте, которую принимает выбранная касса. Проверьте, что staging Remnawave подключена и тариф доступен покупателю.
3. В кабинете кассы получите тестовые ключи и найдите раздел уведомлений. Записывайте секреты в менеджер паролей, а не в этот файл, GitHub или скриншоты.
4. На **staging VDS** подключитесь по SSH и проверьте состояние, заменив адрес на свой:

   ```bash
   cd /opt/vpn-shop
   sudo docker compose --env-file .env config --quiet
   sudo docker compose ps
   curl -fsS https://api.stage.vpn.example.com/health/ready
   ```

   Команда `config --quiet` проверяет конфигурацию, не печатая секреты. Если какая-то команда выдала ошибку, сначала вернитесь к инструкции установки. Не запускайте непонятные команды со случайного сайта.
5. Откройте `sudoedit /opt/vpn-shop/.env` **на staging**. Проверьте `APP_ENV=staging`, `PAYMENTS_SANDBOX=true` и тестовые реквизиты **ровно одной** кассы. Для рабочего VDS эти значения и реквизиты другие. После изменения файла выполняйте `sudo docker compose --env-file .env config --quiet` и перезапускайте сервисы по инструкции установленного релиза.
6. Заведите закрытый протокол: дата и время, среда, версия приложения, название кассы, ID заказа в магазине, provider ID, сумма, валюта, ID события и возврата, статус подписки и результат проверки. Не записывайте номера карт, ключи, токены и полный checkout URL.

## 3. Выберите тип оплаты и точный адрес уведомлений

| Что проверяете | Имя в коде | Куда касса отправляет уведомления на staging | Что понадобится в `.env` |
| --- | --- | --- | --- |
| ЮKassa | `yookassa` | `https://api.stage.vpn.example.com/api/webhooks/yookassa` | `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_WEBHOOK_IP_ALLOWLIST` |
| Platega | `platega` | `https://api.stage.vpn.example.com/api/webhooks/platega` | `PLATEGA_MERCHANT_ID`, `PLATEGA_SECRET`; для возврата ещё согласованные `PLATEGA_REFUND_URL`, `PLATEGA_REFUND_STATUS_URL` |
| RollyPay | `rollypay` | `https://api.stage.vpn.example.com/api/webhooks/rollypay` | `ROLLYPAY_API_KEY`, `ROLLYPAY_SIGNING_SECRET`, `ROLLYPAY_TEST_MODE=true`; для возврата — согласованные URL |
| Stripe | `stripe` | `https://api.stage.vpn.example.com/api/payments/webhooks/stripe` | `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` |
| PayPal | `paypal` | `https://api.stage.vpn.example.com/api/payments/webhooks/paypal` | `PAYPAL_API_URL`, `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID` |
| Криптошлюз | `crypto` | `https://api.stage.vpn.example.com/api/webhooks/crypto` | `CRYPTO_GATEWAY_URL`, `CRYPTO_GATEWAY_KEY` |

**Важно:** это *входящие* адреса вашего магазина. Не вставляйте их вместо API URL самой кассы. Для Stripe и PayPal пути отличаются от `/api/webhooks/...`; не сокращайте их. Если у провайдера нет проверяемой тестовой среды, уведомлений, подлинность которых можно проверить, или рабочего возврата, отметьте проверку как «не пройдена» и не включайте его для клиентов.

## 4. Общая проверка, которую нужно повторить ДЛЯ КАЖДОЙ кассы

Этапы 1–3 ниже можно подготовить сейчас. Этапы 4–9 требуют будущей версии с обычным внешним checkout на staging и полным E2E v2. Не выдавайте результат встроенного v1 за прохождение этих этапов.

1. **Создайте только тестовую учётную запись у кассы.** В её официальном кабинете выберите тестовую среду. Возьмите test-ключи; для RollyPay смотрите особенность ниже: sandbox работает с тем же ключом и специальным флагом. Запишите название магазина и валюту.
2. **Настройте HTTPS webhook.** В кабинете провайдера откройте уведомления/webhooks/callback, вставьте URL из таблицы, сохраните. Включите события успешной оплаты, неуспеха и возврата, **если касса и обработчик проекта их поддерживают**. Запишите ID созданного endpoint/подписки на уведомления и его секрет, если он есть.
3. **Введите тестовые ключи на staging.** Отредактируйте `/opt/vpn-shop/.env` через `sudoedit`, вставьте реквизиты кассы в одноимённые поля из таблицы, сохраните и примените конфигурацию по инструкции релиза. Убедитесь, что внешний тестовый заказ пока блокируется, если всё ещё стоит `v20.0.18`: это ожидаемая проверка закрытого допуска.
4. **После выхода v2 — откройте заказ как staging-покупатель.** В отдельном браузере зайдите в staging кабинет, выберите тариф, нажмите оплату выбранной кассой **один раз**. Запишите ID заказа и сумму. Если страница зависла, сначала найдите заказ у кассы; не нажимайте «Оплатить» ещё раз вслепую.
5. **Завершите тестовую оплату официальным способом кассы.** Убедитесь, что адрес платёжной страницы принадлежит кассе, а не подставному сайту. Настоящую карту в sandbox не вводите, если официальная инструкция не требует и не объясняет этого. Запишите provider ID. Сверьте сумму и валюту у кассы и в заказе.
6. **Проверьте три места:** в кабинете кассы статус успешной операции; в staging админке «Продажи → Платежи» один заказ со статусом `paid` и выполненной выдачей; в staging Remnawave один доступ нужного покупателя на срок тарифа. Отдельно найдите доставку webhook в кабинете кассы. HTTP 200 сам по себе не доказывает выдачу VPN.
7. **Проверьте повтор и отказ.** Штатной функцией кассы повторите доставку **того же** события: не должны появиться второй заказ, списание или доступ. Отдельно проверьте отмену/неудачную тестовую оплату: доступ не должен выдаваться. Проверку неверной подписи и чужой суммы поручите разработчику на staging; не посылайте случайные webhook в production.
8. **Верните тестовую оплату через магазин.** В staging админке найдите тот же платёж → штатный запрос возврата → подтверждение возврата. В кабинете кассы найдите refund ID и конечный статус. Сверьте финансовый журнал магазина и отзыв доступа в Remnawave. Если касса показывает только «принято к обработке», дождитесь окончательного результата. Возврат напрямую в кабинете кассы используйте отдельным тестом уведомления и отзыва: он не заменяет проверку штатной кнопки магазина.
9. **Запишите итог.** PASS возможен только при одном заказе, одном оплаченном provider ID, достоверном webhook, одной выдаче, отсутствии дублей, подтверждённом возврате и отзыве доступа. У встроенного допуска дополнительно должны быть `contract_version=2`, `full_e2e=true`, `status=passed`, актуальная revision и результат моложе 24 часов. Если любой пункт не совпал — FAIL. Повторяйте сценарий с новым тестовым заказом для следующей кассы.

## 5. ЮKassa — какие экраны открыть

1. Откройте личный кабинет ЮKassa → **«Настройки → Магазин»**, выберите *тестовый* магазин, перепишите `shopId` в `YOOKASSA_SHOP_ID` staging. Затем **«Интеграция → Ключи API»**: получите секрет *тестового* магазина и сохраните его в `YOOKASSA_SECRET_KEY`. [Пошаговое описание экранов](YOOKASSA_CLICKS_BEGINNER.md) и [официальное тестирование](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
2. **«Интеграция → HTTP-уведомления»**: укажите `/api/webhooks/yookassa` из таблицы, отметьте доступные `payment.succeeded`, `payment.canceled`, `refund.succeeded`, сохраните. Проверьте официальный список IP уведомлений и доверенных прокси для `YOOKASSA_WEBHOOK_IP_ALLOWLIST`; пустой список здесь приводит к отказу. [Официальные правила уведомлений](https://yookassa.ru/developers/using-api/webhooks).
3. Когда заработает полный v2, откройте тестовую платёжную страницу из заказа, завершите оплату официальными тестовыми данными. Сверьте запись у ЮKassa, webhook, выдачу, затем возврат. [Правила возврата](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds).

## 6. Platega — прежде всего согласуйте тестовый терминал и возврат

1. У Platega получите доступ к **тестовому терминалу**, его merchant ID и secret. Спросите поддержку, есть ли у вашего терминала тестовый платёж, безопасный тестовый возврат, точные URL отмены/проверки возврата и как понимать `accepted`/`manualControlRequired`. Не используйте настоящий терминал для имитации тестового.
2. В личном кабинете **«Настройки → Callback URLs»** вставьте `/api/webhooks/platega` из таблицы. Подтверждение callback идёт с `X-MerchantId` и `X-Secret`; успешный статус — `CONFIRMED`, отмена — `CANCELED`. [Формат callback](https://docs.platega.io/callback-%D0%BE%D0%B1-%D0%B8%D0%B7%D0%BC%D0%B5%D0%BD%D0%B5%D0%BD%D0%B8%D0%B8-%D1%81%D1%82%D0%B0%D1%82%D1%83%D1%81%D0%B0-%D1%82%D1%80%D0%B0%D0%BD%D0%B7%D0%B0%D0%BA%D1%86%D0%B8%D0%B8-29209725e0).
3. Занесите тестовые `PLATEGA_MERCHANT_ID`, `PLATEGA_SECRET` в staging. URL возврата не угадывайте: в текущем проекте они требуют отдельного подтверждения у провайдера. [Проверка возможности отмены](https://docs.platega.io/%D0%BF%D1%80%D0%BE%D0%B2%D0%B5%D1%80%D0%BA%D0%B0-%D0%B2%D0%BE%D0%B7%D0%BC%D0%BE%D0%B6%D0%BD%D0%BE%D1%81%D1%82%D0%B8-%D0%BE%D1%82%D0%BC%D0%B5%D0%BD%D1%8B-%D1%82%D1%80%D0%B0%D0%BD%D0%B7%D0%B0%D0%BA%D1%86%D0%B8%D0%B8-38219023e0).
4. После выхода v2 выполните общие этапы 4–9. Если тестовый возврат недоступен или отмена требует ручных действий, запишите FAIL и оставьте эту кассу закрытой.

## 7. RollyPay — тестовый флаг обязателен

1. В RollyPay откройте **«Платежи → Тестовые»** либо создайте тестовый платёж из официального кабинета с переключателем **«Тестовый платёж»**. У RollyPay sandbox использует **тот же API-ключ, что и рабочая касса**, но запрос обязательно содержит `test: true`; это не отдельный тестовый ключ. На staging поставьте `ROLLYPAY_TEST_MODE=true`, в production это значение запрещено. [Официальный тестовый режим](https://docs.rollypay.io/api/testing/).
2. Используйте согласованные `ROLLYPAY_API_KEY` и `ROLLYPAY_SIGNING_SECRET`, callback `/api/webhooks/rollypay`. На тестовой форме убедитесь, что есть баннер «Тестовый режим», и нажмите симуляцию **успешного** платежа. Затем отдельным новым заказом проверьте кнопку неуспеха. Уведомление содержит `test: true` и `X-Test-Mode: true`; сверяйте подпись и сумму. [Формат callback](https://docs.rollypay.io/api/callbacks/).
3. **Остановитесь перед отметкой PASS:** официальная документация RollyPay прямо сообщает, что тестовые возвраты недоступны. Поэтому обязательный полный сценарий возврата из раздела 4 нельзя подтвердить через sandbox; нельзя подставлять выдуманный URL или заявлять, что касса прошла полный E2E.

## 8. Stripe — тестовый режим и секрет конкретного webhook

1. В Stripe Dashboard включите **test mode / sandbox**, создайте тестовые API-ключи. На staging нужны `STRIPE_SECRET_KEY` из тестового режима и `STRIPE_API_URL=https://api.stripe.com`. Для production ключи будут другими. [Режим тестирования](https://docs.stripe.com/testing/overview).
2. Откройте Stripe Dashboard → **Workbench → Webhooks → Create an event destination** → *Your account* → события, которые реально обрабатывает приложение, → *Webhook endpoint*. Вставьте `/api/payments/webhooks/stripe` из таблицы. Откройте секрет **этого** endpoint с префиксом `whsec_` и внесите в `STRIPE_WEBHOOK_SECRET` staging. Секрет Stripe CLI и секрет live endpoint не взаимозаменяемы. [Официальные шаги](https://docs.stripe.com/webhooks).
3. После появления v2 откройте тестовый Checkout из заказа, завершите оплату [официальной тестовой картой](https://docs.stripe.com/testing), проверьте событие в Workbench, один заказ и выдачу. Повторную доставку выполняйте в интерфейсе Stripe для исходного события. Затем оформите тестовый возврат через магазин и сверяйте его фактический статус у Stripe и отзыв доступа.

## 9. PayPal — две sandbox учётные записи

1. В [PayPal Developer → Sandbox Accounts](https://developer.paypal.com/sandbox-testing/accounts) подготовьте учётную запись **Business** для приёма денег и **Personal** для покупателя. В разделе **Apps & Credentials** выберите *Sandbox*, получите `client_id` и `client_secret` приложения Business. В staging укажите `PAYPAL_API_URL=https://api-m.sandbox.paypal.com`, `PAYPAL_CLIENT_ID` и `PAYPAL_CLIENT_SECRET`.
2. В настройках *Sandbox* приложения откройте **Webhooks → Add Webhook**, вставьте `/api/payments/webhooks/paypal` из таблицы, отметьте события завершения/отказа capture, которые обрабатывает проект. Сохраните ID созданного webhook в `PAYPAL_WEBHOOK_ID`. Для live приложения и его webhook ID будут другие. [Настройка и проверка](https://developer.paypal.com/api/rest/webhooks/rest/).
3. После v2 войдите в Sandbox Personal на странице оплаты staging, завершите один заказ, найдите Business capture ID и событие, затем проверьте выдачу. Возврат выполняйте через магазин и сверяйте статус по capture/refund ID в PayPal. [Официальная процедура возврата](https://developer.paypal.com/checkout/refund-payment). Симулятор webhook не заменяет реальный sandbox заказ: его события могут не пройти серверную проверку подписи для настоящего webhook ID. [Ограничения симулятора](https://developer.paypal.com/api/rest/webhooks/simulator/).

## 10. Криптошлюз — сначала определите конкретного оператора

`crypto` здесь означает **абстрактный внешний шлюз**; проект не выбирает за вас сервис. `CRYPTOBOT_TOKEN` в примере переменных не превращает его автоматически в готовую кассу `crypto`. Нет универсальных кнопок «войти в CryptoBot» и стандартного адреса API для всех шлюзов.

1. Запишите точное название сервиса, его официальную документацию, тестовую сеть/режим, валюту и поддерживаемые возвраты. Сверьте, что его API совместим с контрактом `CryptoGatewayPlatform` в `backend/app/payment_platform.py`; если нет, нужна разработка адаптера.
2. Только после подтверждения совместимости установите на staging `CRYPTO_GATEWAY_URL` и `CRYPTO_GATEWAY_KEY`. В кабинете сервиса добавьте HTTPS callback `/api/webhooks/crypto`. Этот проект ожидает `X-Timestamp` и `X-Signature` с HMAC-SHA256 от `timestamp.raw_body`, затем самостоятельно сверяет платёж через API шлюза.
3. После v2 проверьте тестовый платёж, достаточные подтверждения сети по правилам выбранного сервиса, webhook, одну выдачу, повтор события и фактический возврат/отзыв. Если сервис не умеет проверяемый возврат, пометьте FAIL. Не переводите настоящие монеты на адрес «для проверки» без договорённой процедуры.

## 11. Apple и Google — отдельные покупки внутри приложений

Это не веб-кассы. Для них нет адреса webhook из таблицы: приложение посылает покупку на `/api/payments/mobile/verify`, а сервер проверяет её у Apple/Google. `MOBILE_STORE_PRODUCTS` связывает ID продукта магазина приложений с ID тарифа VPN; без соответствия сервер откажет. **В текущем коде проверка подписи ответа Apple выполняется с `verify_signature=False`: до исправления этого места и отдельного аудита нельзя считать Apple IAP безопасно готовой к живым продажам.** У мобильных покупок также не описан полный встроенный сценарий refund → отзыв доступа для обоих магазинов.

1. **Apple:** в App Store Connect создайте продукт подписки, тестового Sandbox Apple Account и проверьте точный Bundle ID. На staging настройте `APPLE_ISSUER_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`, `APPLE_BUNDLE_ID`, тестовый адрес App Store Server API и `MOBILE_STORE_PRODUCTS`. Сделайте покупку из тестовой сборки, сверьте транзакцию, тариф и выдачу; отдельно испытайте отказ и возврат. [Официальная проверка sandbox и возвратов](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox). До исправления проверки подписи не ставьте PASS.
2. **Google Play:** в Play Console создайте подписку, опубликуйте тестовую сборку в тестовом треке, добавьте Google-аккаунт в license testers. Для staging настройте `GOOGLE_PLAY_PACKAGE`, `GOOGLE_SERVICE_ACCOUNT_JSON`, `MOBILE_STORE_PRODUCTS`; проверьте совпадение package name. Сделайте тестовую покупку на устройстве тестировщика, сверьте токен/ID продукта и один доступ. Проверьте возврат с отзывом доступа. [Официальная инструкция Google](https://developer.android.com/google/play/billing/test). До реализации полного отзыва доступа не ставьте PASS.

`sepa` в коде помечен как банковский перевод/счёт, а не redirect checkout; `sandbox` — внутренняя имитация без денег; кошелёк и подарочная карта не являются внешними кассами. Не заменяйте ими проверку поставщика.

## 12. Настоящие деньги: отдельная проверка ПОСЛЕ исправления проекта

**Сейчас этот раздел выполнять нельзя.** Сначала нужен выпущенный код с безопасным полным E2E v2 **для конкретного провайдера**, подтверждённые возвраты и отзыв доступа, проверка актуальной версии на двух VDS, договор с кассой и разрешённый live-магазин. Текущий встроенный runner настроен прежде всего на ЮKassa, Platega и RollyPay; он не доказывает готовность Stripe, PayPal, криптошлюза или мобильных покупок. Сам факт будущего `full_e2e=true` для одной кассы не доказывает остальные.

1. В официальном кабинете **каждой** кассы переключитесь с test/sandbox на live/рабочий магазин. Получите именно рабочие ключи и отдельные рабочие webhook credentials. Проверьте, что доступны нужные вам способы оплаты, валюта, возвраты и требования к чекам. Не копируйте staging `.env` на production.
2. В live-кабинете этой кассы создайте новое уведомление на тот же путь из таблицы раздела 3, заменив `api.stage.vpn.example.com` на **ваш рабочий** `api.vpn.example.com`. Для Stripe скопируйте live `whsec_`; для PayPal — live webhook ID. Для RollyPay должно быть `ROLLYPAY_TEST_MODE=false`; у Stripe и PayPal нужны рабочие ключи и рабочий API URL PayPal `https://api-m.paypal.com`.
3. На **рабочем** VDS проверьте `APP_ENV=production`, `PAYMENTS_SANDBOX=false`, `COOKIE_SECURE=true`, `WEBHOOK_BASE_URL=https://api.vpn.example.com` и рабочие реквизиты выбранной кассы. Выполните `sudo docker compose --env-file .env config --quiet` и перезапустите сервисы только по инструкции нового релиза. Проверьте `/health/ready` и резервную копию.
4. В рабочей админке **«Безопасность → Безопасность»** посмотрите результат полного E2E именно для этой кассы. Если кнопка «Разрешить реальные платежи» недоступна или сервер отвечает 409, остановитесь: это не ошибка браузера, которую надо обходить. Включайте допуск только если сервер разрешает это штатным образом и подтверждены остальные провайдерские проверки.
5. Из **отдельного аккаунта покупателя** купите **один** тариф на минимальную допустимую кассой сумму. Это настоящее списание. Запишите ID у кассы; сверьте **один** заказ, фактическое поступление денег, правильную сумму и валюту, доставку webhook, запись финансового журнала и **один** доступ в рабочей Remnawave. Не запускайте сразу несколько касс и не создавайте повторный заказ при задержке.
6. Через штатный маршрут магазина выполните полный либо разрешённый частичный возврат, дождитесь конечного статуса у провайдера, сверьте финансовый журнал и отзыв доступа. При расхождении остановите новые продажи кнопкой **«Заблокировать»** и разберите ID операции с поддержкой провайдера. Самостоятельно включать продажи до исправления нельзя.

Повторите эти шесть шагов **отдельно** для каждой кассы, которую действительно планируете предложить покупателям. Для RollyPay и провайдеров без sandbox refund прежде решите блокер тестового полного возврата с провайдером и разработчиком: нельзя выдавать реальное списание за эквивалент полноценного теста без продуманной процедуры и подтверждения безопасности.

## 13. Как заполнять протокол и что делать при ошибке

Скопируйте строку ниже в **закрытый** внутренний журнал для каждого нового заказа:

| Поле | Значение |
| --- | --- |
| Среда, дата и версия | staging / ДД.ММ.ГГГГ ЧЧ:ММ UTC / тег и commit |
| Касса и режим | имя / test или sandbox |
| Тариф и сумма | ID / сумма / валюта |
| Идентификаторы | order ID / provider ID / webhook ID / refund ID / Remnawave ID |
| Заказ, webhook, доступ | по одному, сумма и валюта совпали: да/нет |
| Повтор webhook и неуспешная оплата | дублей нет, доступ не выдан: да/нет |
| Возврат и отзыв доступа | конечный статус у кассы и в магазине: да/нет |
| Встроенный E2E | run ID / revision / `contract_version` / `full_e2e` / `status` |
| Решение | PASS только если всё выше «да»; иначе FAIL и причина |

Если платёж у кассы успешен, а в магазине нет VPN: **не создавайте новый платёж**. В рабочей админке закройте новые оплаты кнопкой «Заблокировать», сохраните ID и время, найдите webhook и статус выдачи, проверьте Remnawave. Если webhook не дошёл, проверьте URL, HTTPS, журнал доставки у кассы и журнал backend (`cd /opt/vpn-shop && sudo docker compose logs --tail=100 backend worker`). Логи могут содержать личные данные: не публикуйте их целиком. Если возврат только «запрошен», дождитесь конечного статуса у кассы и отдельно проверьте отзыв доступа.

**Переход к живой контрольной покупке** после реализации v2 расписан в [общем маршруте реальных платежей](REAL_PAYMENTS_FROM_ZERO.md). Включайте по одной кассе; реальная контрольная покупка списывает настоящие деньги. До получения полного PASS каждой конкретной интеграции держите её недоступной для покупателей.
