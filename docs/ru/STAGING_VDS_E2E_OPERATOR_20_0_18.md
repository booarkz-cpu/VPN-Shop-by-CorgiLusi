# Реальный VDS и staging E2E платежей: инструкция оператора для v20.0.18

**Статус версии:** сервер и изолированный тестовый контур можно подготовить и проверить. Полный staging E2E v2 в v20.0.18 **не реализован**. Нельзя получить подтверждённый `full_e2e=true` и открыть приём живых платежей штатным способом. Эта инструкция не предлагает обходить защиту изменением базы или исходников на рабочем сервере.

## 1. Что подготовить

1. Возьмите **два отдельных VDS**: production и staging. Для каждого нужны Ubuntu 24.04 LTS или Debian 12, доступ SSH с `sudo`, публичный IPv4, минимум 2 vCPU, 4 ГБ RAM и 30 ГБ свободного места. Не используйте общую базу, Redis, Remnawave, бот, домены, ключи или callback между контурами.
2. Создайте отдельные DNS имена `api`, `admin`, `app`, `cabinet`, `support` для каждого VDS: например `api.vpn.example.com` и `api.stage.vpn.example.com`. Для каждого имени добавьте запись A с IP нужного сервера. Удалите ошибочные AAAA, если IPv6 не настроен. Откройте внешний TCP 80/443 и свой SSH порт.
3. Получите отдельные токены ботов в @BotFather и отдельную тестовую панель Remnawave. Для staging возьмите только sandbox credentials провайдера. Узнайте в его официальном кабинете, доступны ли подписанный webhook, тестовый возврат и повторная доставка события. Если хотя бы один этап недоступен, этот провайдер не может получить полный PASS.
4. Заведите менеджер паролей для секретов и защищённое место **вне обоих VDS** для резервных копий. Не отправляйте ключи, вывод `.env`, checkout URL и логи с клиентскими данными в чат или GitHub.

## 2. Установить production VDS, оставив платежи закрытыми

Войдите по SSH на production VDS. Если вы новичок, выполните подробную [инструкцию установки v20.0.18](VDS_PRODUCTION_20_0_18.md) от начала до конца. На вопрос установщика о платёжном провайдере выберите `none`. Не включайте `PAYMENTS_SANDBOX` на production.

Проверка после установки (замените домен):

```bash
cd /opt/vpn-shop
sudo docker compose --env-file .env config --quiet
sudo docker compose ps
curl -fsS https://api.vpn.example.com/health/ready
```

Проверьте в админке вход с MFA, работу тестового тарифа, Mini App и связь с Remnawave **без оплаты**. Убедитесь, что новые боевые платежи отклоняются сообщением о необходимости staging E2E. Это ожидаемое безопасное состояние.

## 3. Установить отдельный staging VDS

Повторите шаги 0–5 [инструкции установки v20.0.18](VDS_PRODUCTION_20_0_18.md) **на другом сервере**, используя исключительно staging домены, отдельный бот и отдельную Remnawave. Установщик создаёт конфигурацию с `APP_ENV=production` и запрещает `PAYMENTS_SANDBOX=true`, поэтому сначала установите его с ответом `false`, а затем измените **только staging** конфигурацию:

```bash
cd /opt/vpn-shop
sudoedit .env
```

Найдите и установите строки `APP_ENV=staging` и `PAYMENTS_SANDBOX=true`, сохраните файл. Проверьте, что домены и токены в этом файле относятся к staging. Затем перезапустите приложение:

```bash
sudo docker compose --env-file .env config --quiet
sudo docker compose up -d --build
sudo docker compose ps
curl -fsS https://api.stage.vpn.example.com/health/ready
```

Установите тестовый тариф с небольшой положительной ценой и отдельного тестового покупателя. Сделайте пробный backup staging и восстановите его на другом чистом стенде до проверки возвратов. Не используйте для испытания настоящие карты и production credentials.

## 4. Подготовить провайдера и webhook

Для каждого провайдера по отдельности:

1. Включите sandbox в **официальном** кабинете провайдера, получите тестовые ключи и инструкции по тестовой оплате/возврату. Уточните его действительный URL API, формат подписи и правила IP allowlist. Не угадывайте значения.
2. Установите тестовые credentials на staging. Сверьте имя провайдера и путь callback: YooKassa — `https://api.stage.vpn.example.com/api/webhooks/yookassa`, Platega — `/api/webhooks/platega`, RollyPay — `/api/webhooks/rollypay` на том же домене. Проверьте, что провайдер действительно доставляет события по HTTPS. Полный путь и способ подтверждения событий сверяйте с кабинетом провайдера.
3. Запишите тестовые ID заказа, платежа и события, сумму и валюту, не сохраняя данные карты или полный URL оплаты в общем отчёте.

**Текущий блокер:** `POST /api/payments/create` для любого провайдера, кроме внутреннего `sandbox`, проверяет production gate даже при `APP_ENV=staging`; gate в v20.0.18 не может открыться. Поэтому настоящий пользовательский checkout с внешним sandbox провайдером сейчас вернёт `503`. Не снимайте это ограничение вручную на production.

## 5. Что можно проверить встроенным runner v1

В **production-админке** сохраните конфигурацию проверки, указывающую на отдельный staging HTTPS API, staging Remnawave, staging-тариф и sandbox credentials. Именно база production хранит результат, который читает production gate. Отдельно убедитесь, что production сервер не использует staging ключи для обычной оплаты. Для Platega и RollyPay форма потребует официальные HTTPS адреса возврата и проверки статуса; не придумывайте их. Запустите проверку и завершите **тестовую** оплату по checkout URL в разрешённом провайдером sandbox. Следите за статусом в production-админке. Текущий runner выполняется внутри production backend и вызывает его локальные служебные endpoints; не путайте это с обычным checkout на staging.

**Ограничение провайдеров:** RollyPay в опубликованном описании sandbox не поддерживает возвраты; тестовый платёж не сможет пройти обязательный шаг refund. Нельзя заполнять произвольный URL возврата ради прохождения формы. Для Platega наличие тестового контура и семантику `accepted`/`manualControlRequired` возврата надо подтвердить у провайдера. До этого не считайте их пригодными для полного PASS.

Runner проверяет ответы API провайдера, возврат и доступность Remnawave. Он печатает `[INCOMPLETE]`; результат имеет `contract_version=1`, `full_e2e=false`. Даже успешные строки `[PASS]` **не подтверждают** webhook, запись `Payment`, выдачу VPN, идемпотентность и отзыв доступа. Не используйте этот результат для допуска боевых платежей.

Если checkout не открылся, webhook не приходит или возврат не подтверждён, проверьте DNS, HTTPS, firewall, sandbox ключи и официальный кабинет провайдера. Не запускайте повторное списание при неопределённом статусе: сначала сверьте ID в кабинете.

## 6. Критерии полного staging E2E v2 после реализации

Следующие шаги являются **приёмочными критериями будущего runner v2**, а не работающей процедурой v20.0.18. Для каждого провайдера нужны связанные доказательства одного запуска и одного внутреннего заказа:

1. Тестовый покупатель создаёт заказ обычным `POST /api/payments/create` с новым `Idempotency-Key`. Повтор с тем же ключом сохраняет один заказ и один provider intent. Сверяются `Payment.id`, `order_id`, provider ID, тариф, сумма и валюта.
2. Покупатель оплачивает заказ на официальной sandbox странице. Провайдер доставляет **подписанный** webhook на staging. Приложение связывает его с тем же заказом и подтверждает `paid`; один только polling провайдера не засчитывается.
3. Worker создаёт ровно одну подписку и один доступ в staging Remnawave. Проверьте срок и лимит по конкретному удалённому ID. Отказ Remnawave должен приводить к безопасному повтору без второй выдачи.
4. Провайдер повторно доставляет то же событие с действительной подписью. Заказ, финансовый журнал, подписка и доступ не дублируются. Неверная подпись, сумма, валюта или чужой ID отклоняются без изменения состояния.
5. Администратор создаёт запрос возврата для этого `Payment`, подтверждает его и выполняет через штатный маршрут магазина. Проверьте подтверждение возврата у провайдера, запись финансового события, отзыв доступа в Remnawave и отсутствие повторного возврата. Поздний success webhook не возвращает доступ.
6. Сервер, а не ручная отметка, вычисляет `contract_version=2`, `full_e2e=true`, `status=passed` по связанным событиям и текущей revision конфигурации. Для любого пропущенного шага итог — отказ. Повторите весь цикл для **каждого** провайдера, который планируется использовать в production.
7. Лишь после нового релиза с реализованным v2, CI и настоящего sandbox прогона, не старше 24 часов, уполномоченный администратор может включить production gate через панель. Проверьте его автоматическое закрытие при устаревании результата или смене конфигурации. До этого момента ожидаемый ответ на включение — `409`.

Подробная [матрица приёмки и проектный контракт v2](STAGING_E2E_V2_IMPLEMENTATION.md) описывают дополнительные отрицательные сценарии и доказательства.

## 7. Когда остановиться и что сохранять

Остановитесь, если перепутаны ключи или callback двух сред, нет подписанного sandbox webhook, нет подтверждённого возврата, пропала связь с Remnawave или статус заказа неоднозначен. Выключите платежи штатным gate, сохраните внутренние ID операций, проверьте фактический статус у провайдера и восстановите стенд из проверенной копии, если нужно. Нельзя править `staging_e2e.status`, `payments.production_gate.v20_0_8` либо БД вручную ради отметки PASS.

Для итогового акта сохраняйте обезличенные run ID, revision, commit/tag, время, провайдера, внутренний и внешний ID платежа, ID webhook/возврата, проверки дублей и факт отзыва доступа. Секреты и персональные данные в акт не включайте.
