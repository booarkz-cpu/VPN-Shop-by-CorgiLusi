# Импорт users.db и массовые операции клиентов

Этот этап добавляет перенос **Telegram ID и имени** из SQLite и массовое управление доступом к магазину. Это не полный перенос другого бота: деньги, реферальные связи, пароли, email, платежи и VPN-подписки требуют отдельных правил сверки и не импортируются.

## Подготовка и установка

1. Сделайте согласованный backup PostgreSQL и файлов магазина по текущей production-инструкции. Проверьте восстановление на отдельном стенде.
2. Разверните код этого изменения вместе с админкой и выполните `alembic upgrade head` в backend. Новая миграция — `0058_customer_operations`, после `0057_partner_commissions`.
3. Используйте роль operator или admin с правом `users.write`. Viewer не может читать загружаемую базу, предпросмотр или журнал операций.
4. Откройте **Клиенты магазина → Импорт пользователей и массовые операции**. Раздел есть в CRM и карточке клиента 360.

## Импорт

1. Остановите запись в исходную базу и создайте автономную SQLite-копию через SQLite backup API или `.backup`. Простое копирование `users.db` без WAL может потерять последние записи. Загружайте только доверенную резервную копию вашего бота.
2. Выберите файл до **8 МиБ**, нажмите «Прочитать таблицы». Допускается до 50 обычных таблиц; представления и виртуальные таблицы не импортируются.
3. Укажите понятное название источника, таблицу, колонку Telegram ID и необязательную колонку имени. Колонки `id` и `telegram_id` не считаются взаимозаменяемыми автоматически: выберите именно Telegram ID.
4. Нажмите «Предпросмотр импорта». В одной операции допускается 1–5000 строк. ID должен быть положительным целым до `2^52−1`; имя — текстом до 255 символов. Дубли, пустые и некорректные ID блокируют весь файл; исправьте копию и повторите проверку.
5. Проверьте **все строки**. Новые ID получают действие «Создать», уже существующие или ранее импортированные — «Пропустить». Существующие имена, ограничения, балансы и реквизиты не меняются.
6. Подтвердите список и нажмите «Применить» в течение 15 минут. Выполняется одна транзакция. Если состояние клиентов изменилось или возникла гонка регистрации/импорта, операция возвращает 409 и требует нового предпросмотра.
7. Сверьте журнал. Повторное применение того же ID операции возвращает тот же результат без новых пользователей. Новый импорт той же базы также пропускает старые ID, даже если ранее импортированный аккаунт был обезличен.

Импорт не отправляет сообщения, не выдаёт VPN и не переносит право доступа по email. Новый аккаунт получает обычные нулевые балансы и авторизуется штатным способом Telegram.

## Массовые действия

Введите **внутренние ID магазина**, до 500 разных положительных ID, выберите действие и укажите причину. Предпросмотр показывает конкретные аккаунты и строки без изменений. Отсутствующий или удалённый аккаунт блокирует всю операцию.

- **Ограничить доступ к магазину**: выставляет `restricted_at`, отзывает действующие клиентские сессии, коды обмена авторизации и запросы сброса пароля. Общая проверка клиентской сессии запрещает доступ ограниченному аккаунту.
- **Восстановить доступ к магазину**: снимает ограничение. Отозванные сессии не восстанавливаются — клиент входит заново.

Эти действия **не отключают и не восстанавливают VPN в Remnawave**, не меняют баланс, срок подписки или автопродление. Для блокировки сетевого доступа используйте соответствующий процесс управления VPN. Перед снятием ограничения проверьте исходную причину, в том числе антиабуз.

Операция привязана к администратору, создавшему предпросмотр. Изменение выбранного аккаунта после проверки требует нового предпросмотра. Повтор запроса после потери соединения безопасен: используйте тот же ID операции.

## Журнал и хранение

В интерфейсе показаны последние 50 собственных операций: время, источник/причина, статус, результат по внутренним ID клиентов. Успешные операции также попадают в общий audit log. Неприменённые предпросмотры имеют статус preview/expired, ошибки запроса возвращаются оператору и не записываются как успешный импорт.

Исходный файл читается в памяти и не сохраняется. Нормализованные имена и Telegram ID хранятся в PostgreSQL до применения; при успехе исходные строки удаляются из payload. Просроченные payload очищаются при создании следующего предпросмотра. До этого они могут оставаться в БД и backup. Постоянный реестр Telegram ID сохраняется для защиты от повторного импорта; учитывайте его в политике хранения данных.

После применённых операций downgrade миграции запрещён: он уничтожил бы журнал и защиту от повторов. Возврат выполняется восстановлением согласованного backup с учётом новых данных после его создания.

## API

Все пути начинаются с `/api/admin/customer-operations`, используют штатную admin-аутентификацию и CSRF.

| Метод и путь | Назначение |
| --- | --- |
| POST `/import/inspect` | Тело — двоичный SQLite; возвращает таблицы и колонки |
| POST `/import/preview?source=…&table=…&telegram_column=…&username_column=…` | Тело — тот же SQLite; сохраняет проверенные строки и возвращает ID предпросмотра |
| POST `/bulk/preview` | JSON: `action` restrict/unrestrict, `user_ids`, `reason` |
| POST `/{operation_id}/apply` | Применяет собственный предпросмотр; его ID служит ключом повторного запроса |
| GET `/journal` | Последние 50 собственных операций |

## Проверка перед production

На стенде проверьте смешанную базу с новым и существующим Telegram ID, повтор apply, повторную загрузку, просрочку, чужого администратора, viewer, изменение клиента после preview и отзыв сессии при ограничении. Запустите `tests/test_customer_operations.py`; проверки гонок выполняются при наличии `AUDIT_TEST_DATABASE_URL` с PostgreSQL. Типизация и сборка админки: `npm run typecheck`, `npm run build`.

Этот этап не меняет `production_e2e_verified=false`, `full_function_transfer=false` и требования к внешнему платёжному E2E и подписанным приложениям.
