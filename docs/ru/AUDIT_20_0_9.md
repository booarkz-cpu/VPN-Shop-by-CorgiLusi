# Аудит v20.0.9 — 25 сентября 2026

База: `1708b8c`, актуальный `main` после v20.0.8. Проверены авторизация и сессии, подтверждение оплаты, кошелёк и возвраты, повторная выдача, фоновые задачи, доступ Support Pro, зависимости и путь публикации. Аудит не доказывает отсутствие всех возможных ошибок и не заменяет тестирование реальных касс и VPN-инфраструктуры.

## Подтверждённые дефекты и исправления

| Приоритет | Дефект и последствие | Исправление |
| --- | --- | --- |
| Критический: деньги | Возврат пополнения обрабатывался как возврат подписки: средства оставались в кошельке, могла отключиться отдельная подписка. | Отдельная транзакционная отмена пополнения. Блокировка платежа, уникальный ключ финансового журнала, атомарное уменьшение баланса, savepoint для отката при ошибке. Повтор и конкурентный повтор не списывают дважды. Незачисленное пополнение не списывается. |
| Высокий: конкурентность | SQLAlchemy при повторном SELECT FOR UPDATE мог вернуть старые атрибуты из identity map. Предварительно прочитанный paid/deleted_at мог пережить чужую транзакцию. | `populate_existing=True` в критических повторных чтениях платежей, пользователей, возвратов и подписок. |
| Высокий: аккаунты | VK автоматически привязывался к существующему email без подтверждения владения локальным аккаунтом. Регистрация по email не проверяет адрес, поэтому могла сохранить пароль и сессии злоумышленника в объединённом аккаунте. | Автоматическое объединение запрещено; 409 без записи при коллизии. Действующие vk_id продолжают работать. |
| Высокий: расчёты | Platega/RollyPay проверяли сумму и заказ, но игнорировали валюту; staging также безусловно принимал валюту. | Отсутствующая и несовпадающая валюта отклоняются. Нельзя считать равные числа в разных валютах равными платежами. |
| Усиление сессий | AdminSession не сравнивался с admin.id; часть входов могла выпускать сессии удалённому пользователю. | Проверка владельца админской сессии; общий запрет создания пользовательской сессии после удаления; VK не выпускает exchange-код удалённому аккаунту. |
| Достоверность журнала | Email/VK audit считывал X-Forwarded-For без проверки доверенного прокси. | Используется общий обработчик IP с проверкой доверенного прокси. |

Отрицательный баланс после возврата потраченного пополнения намеренный: это долг. Обнуление вместо списания создало бы деньги. Возврат не отзывает подписку, приобретённую отдельным платежом.

## Проверки

- Локально: Python backend — 394 успешно, 7 пропущены (6 PostgreSQL-проверок и существующий опциональный тест); исполняемые регрессии с HTTP-моками; Support Pro — 36 тестов.
- Три веб-интерфейса: `npm ci`, `npm run typecheck`, `npm run build`, `npm audit --audit-level=high`.
- `pip-audit` backend: известных уязвимостей не найдено на дату проверки. Проверка всех четырёх Python requirements и трёх npm lock-файлов также обязательна в CI.
- PostgreSQL-регрессии запускаются в CI: повтор возврата, конкурентные возвраты, потраченный и незачисленный баланс, откат после ошибки журнала, устаревший paid после возврата.
- GitHub CI также выполняет миграции, проверку Compose и отдельный набор Support Pro. Публикация разрешается только после успешного push CI на точном коммите main.
- Локально PostgreSQL/Docker недоступны; соответствующие проверки выполняются на GitHub, а не объявляются прошедшими локально. Окончательный результат смотрите в Actions для коммита релиза.

## Обновление и сверка истории

1. Сделайте резервную копию БД, `.env`, media и Support Pro. Проверьте восстановление на отдельном стенде.
2. Обновите исходники штатным `scripts/update-from-github.sh` после публикации тега v20.0.9 либо разверните сам тег через существующий процесс. Новых миграций в этом релизе нет.
3. Проверьте `/health/ready`, входы, кабинет, Support Pro и локальную песочницу. Live-платежи не включайте: полноценный E2E по-прежнему не реализован.
4. Найдите уже возвращённые и ранее зачисленные пополнения без корректирующей записи:

```sql
SELECT p.id, p.user_id, p.amount, p.currency, p.status
FROM payments p
WHERE p.purpose = 'topup'
  AND p.fulfillment_status = 'completed'
  AND p.status IN ('refunded', 'refunded_pending_revoke')
  AND NOT EXISTS (
    SELECT 1 FROM financial_ledger f
    WHERE f.operation_key = 'wallet-topup-refund:' || p.id::text
  );
```

5. Для найденных операций сверьте факт возврата у провайдера и существующий RefundRequest. После обновления выполните штатный `POST /api/admin/refunds/{refund_id}/reconcile` авторизованным администратором с CSRF и правом `payments.reconcile`. Это изменяет баланс, поэтому выполняется только после сверки. При отсутствующем provider_refund_id сначала выясните состояние у провайдера; не подставляйте вымышленные идентификаторы.
6. Если старый возврат пополнения ошибочно отключил VPN, отдельно проверьте оплаченный срок и восстановите законную подписку штатными действиями. Релиз не продлевает сроки автоматически.
7. Проверьте старые VK/email-привязки, если совместно присутствуют vk_id и пароль и есть признаки чужих сессий. Автоматического удаления исторических привязок и сессий нет; восстановление доступа требует подтверждения владельца.

## Границы

Нет доступа к рабочему VDS, реальным платёжным операциям, Remnawave и ключам магазинов приложений. Проверки HTTP-моками и тестовой PostgreSQL не подтверждают контракт внешнего провайдера. Если API провайдера не возвращает валюту в поддерживаемом поле, платёж остаётся неподтверждённым до адаптации по официальному контракту. Нельзя обходить проверку установкой currency_ok=True.
