# Обновление существующего магазина

v21.0.1 stable фиксирует текущее проверенное ядро. Production E2E и полный перенос функций не завершены. Для ознакомления используйте отдельный стенд. Не запускайте обновление действующего магазина без резервной копии и проверки новой схемы.

## Перед обновлением

1. Запишите текущий commit/tag и способ развёртывания.
2. Убедитесь, что нет неопределённых платежей и выполняющегося восстановления.
3. Снимите резервную копию базы и файлов, проверьте чтение архива.
4. Сохраните серверный `.env` отдельно с ограниченным доступом; не добавляйте его в Git.
5. Проверьте свободное место и доступ к Docker/GitHub.
6. Если ранее использовались другие агенты, сохраните их credentials для сверки исторических операций. Новые оплаты через них будут недоступны.

```bash
cd /opt/vpn-shop
docker compose ps
# Создайте полный backup через админку и подтвердите восстановление.
git status --short
git rev-parse HEAD
```

Если есть собственные изменения, перенесите их в отдельную ветку и сравните до обновления. Не используйте `git reset --hard` для их удаления.

## Выбрать стабильный выпуск ядра

После резервного копирования и сохранения собственных изменений:

```bash
git fetch origin
git switch --detach v21.0.1
```

Тег фиксирует проверенный CI commit; `main` может изменяться после выпуска.

## Новые миграции

Миграция `0042_workspace_withdrawals` добавляет nullable `idempotency_key` и уникальность `(user_id, idempotency_key)` в `withdrawal_requests`. Старые строки сохраняются. Ключ защищает новые повторные заявки от второго резервирования баланса.

Миграция `0043_support_conversations` добавляет историю сообщений и уникальные ключи повторной отправки. Существующий последний ответ каждого оператора переносится в историю. Начальный вопрос остаётся в обращении; старые API-проекции сохраняются. До запуска нового backend обязательно примените все миграции до head.

Миграция `0044_subscription_commerce` добавляет пакеты трафика, неизменяемые расчёты/операции и стоимость дня подписки. Старые подписки сохраняются. Откат 0044 удаляет историю этих заказов: при наличии финансовых операций используйте исправление вперёд, предварительно экспортировав таблицы.

Миграция `0045_multiple_subscriptions` сохраняет старые записи и назначает первый профиль каждого владельца выбранным. Старые заказы подписок, устройства, триалы и активации подарков привязываются к нему. Настройка автопродления переносится на этот профиль. Если в старой базе уже есть несколько строк одного владельца, выбирается минимальный ID: оператор должен проверить привязку старых заказов до обработки.

Миграция `0046_gift_snapshots` фиксирует условия существующих подарков из текущего каталога и добавляет снимок активации для повторов. Исторические условия уже изменённого тарифа автоматически восстановить нельзя: сверяйте такие подарки до обновления. Новые покупки сохраняют условия непосредственно при продаже.

Миграция `0047_support_attachments` добавляет приватные вложения в PostgreSQL. Файлы не попадают в публичный media-каталог. Backup базы включает файлы. Downgrade удаляет все вложения: экспортируйте их до отката.

```bash
docker compose build backend worker bot admin cabinet miniapp
docker compose run --rm backend alembic upgrade head
docker compose up -d backend worker bot admin cabinet miniapp
docker compose ps
```

Проверьте фактическое имя сервиса backend в вашем compose. В действующем проекте Alembic находится в образе backend. Существующий штатный `scripts/update.sh` содержит резервирование и проверку состояния; для установки из релиза используйте его регламент. Простое скачивание `main` не является установкой нового опубликованного релиза.

## Head alpha.6 — 0052_giveaways

Выполните все миграции до `0052_giveaways`. 0048 добавляет мост поддержки, 0049 — условия автопродления, 0050 — recovery/email actions, 0051 — опросы, 0052 — конкурсы и колесо. Проверьте `docker compose exec -T backend alembic current` после запуска. 0052 добавляет только таблицы акций и участия; существующие заказы/балансы не меняются. Downgrade запрещён при наличии любого участия. Исправление вперёд предпочтительно; полный restore выполняйте только из проверенной согласованной копии.

Для собственного CMS-меню добавьте вкладку `kind=giveaways`; стандартное меню обновляется автоматически. Не меняйте подтверждение email в БД для обхода условий наград. [Инструкция](WORKSPACE_GIVEAWAYS.md).

Production GitHub Deploy требует точный stable `release_tag`; alpha отклоняется. Новый updater поддерживает `RELEASE_TAG=vX.Y.Z`; старые серверные updater сначала обновите вручную. Существующая версия выше выбранного тега не понижается. [Эксплуатация](../../OPERATIONS_RUNBOOK_RU.md).

## Что поменяется

- Меню админки сгруппировано по задачам; несколько старых обзорных страниц скрыты из обычной навигации.
- Карточка клиента выбирается из поиска, а не из заранее заданного пользователя №1.
- Кабинет получил страницы кошелька, платежей, подписки, подарков, рефералов, уведомлений и безопасности.
- Встроенные страницы объединяются по виду и slug; старое сохранённое меню получает недостающие основные страницы.
- Mini App использует общие исходники кабинета. Docker context Mini App теперь корень репозитория; его Dockerfile копирует `cabinet`.
- Локальная standalone-сборка Mini App требует зависимости кабинета. Админка использует общий компонент вложений; её Docker build context теперь корень репозитория с Dockerfile `admin/Dockerfile`. Vite устраняет дубли React при импорте общих компонентов.
- Новые агенты ограничены тремя; Apple/Google receipt checkout отключён.
- Сине-фиолетовая палитра применяется к веб интерфейсам и исходникам мобильных клиентов.
- Ответ на обращение создаёт уведомление клиента; точный повтор ответа не дублирует его.

## Проверка после обновления

Откройте админку и кабинет в новом приватном окне, чтобы не использовать старый JS из кеша. Проверьте вход, 2FA и CSRF. Создайте тестовый тариф, проведите покупку в sandbox, дождитесь выдачи доступа. Проверьте кошелёк, подарок, повтор активации, заявку на выплату и ответ поддержки. В Telegram проверьте `/account`, ссылку приглашения, переходы в страницы и кнопки Mini App.

Проверьте запросы `/api/payments/providers` и публичный конфиг. В коммерческом каталоге должны быть только `yookassa`, `rollypay`, `platega`. Тестовый sandbox показывается только на допустимом окружении. Старые payment records должны оставаться в истории.

## Мобильные приложения

Изменения исходников не обновляют APK/IPA, уже установленные у пользователей. Для новых цветов и функций соберите, подпишите и распространите новые клиентские и административные приложения по мобильной инструкции. CI проверяет Android/iOS отдельно. Apple/Google встроенные покупки теперь закрыты сервером, даже если старый клиент пытается их вызвать.

## Откат

Остановите новые операции, сохраните состояние после обновления и сравните миграции. Если требуется downgrade, сначала оцените новые заявки с ключами: откат 0042 удаляет ключи, хотя сами заявки остаются. Откат 0043 удаляет всю новую переписку: сначала экспортируйте `support_messages`, если она нужна. Downgrade 0045 запрещён, если у владельца осталось несколько подписок. Downgrade 0046 удаляет снимки подарков; перед любым откатом экспортируйте эти данные. Для финансовых данных предпочтительнее исправление вперёд. Для полного восстановления используйте проверенный дамп и штатный регламент; не подменяйте текущую базу старым дампом без анализа новых платежей.

## Локальная проверка разработчика

```bash
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt -r backend/requirements-test.txt
APP_ENV=test APP_SECRET=test-only-secret PYTHONPATH=backend .venv/bin/python -m pytest -q tests
(cd admin && npm ci && npm run typecheck && npm run build)
(cd cabinet && npm ci && npm run typecheck && npm test && npm run build)
(cd miniapp && npm ci && npm run typecheck && npm run build)
```

SQLite-тесты новых проекций не проверяют PostgreSQL advisory locks. CI содержит отдельные PostgreSQL-регрессии, миграции, Compose и native-сборки. Для E2E реальной кассы необходим внешний стенд и корректные credentials.


Docker-публикация v21.0.1 stable обновляет `latest`, тег ветки и SHA. Alpha-сборки используют `preview` и не заменяют `latest`. Публикуются образы backend, bot, admin, cabinet и miniapp. Для воспроизводимого развёртывания закрепляйте image digest.

## Переход alpha.2 → alpha.3

Магазин получает `0048_support_bridge`: стабильные ссылки импорта и индекс изменённых обращений. Support Pro получает `0005`: номера связанных обращений/файлов, курсор и состояние синхронизации. Существующая история не меняется до настройки и отдельного `--apply`. После появления ссылок downgrade запрещён; восстановление должно использовать согласованные backup двух баз и uploads. Архив alpha.2 остаётся с миграцией 0047, новый архив alpha.3 содержит 0048.

Настройка, команды для общего/самостоятельного Compose, preview и возобновление переноса: [WORKSPACE_SUPPORT_BRIDGE.md](WORKSPACE_SUPPORT_BRIDGE.md). Новым установкам ключ создаёт установщик; существующим — `scripts/configure-support-bridge.py`. Секрет SSO не заменяется ключом переписки.

## Переход alpha.3 → alpha.4

`0049_renewal_terms` добавляет снимок продления конструктора. Существующие подписки не переписываются: известный последний полный grant используется для восстановления условий, а неоднозначные исторические изменения блокируют автоматический новый charge. `0050_account_actions` добавляет отметку email, одноразовые действия и зашифрованную очередь писем. Support Pro остаётся на `0005`.

Примените head до запуска нового backend/worker. Downgrade 0049 запрещён при сохранённых renewal snapshots; полный возврат требует согласованного backup. Downgrade 0050 удаляет ссылки/очередь и отметки email, но не возвращает прежние пароли или отозванные сессии. Безопаснее исправление вперёд.

SMTP/HTTPS адрес кабинета и действия пользователя: [безопасность аккаунта](WORKSPACE_ACCOUNT_SECURITY.md). Порядок проверки без внешнего стенда: [готовность выпуска](FINAL_RELEASE_READINESS.md). Лицензия 2.1 сохраняет разрешение собственного коммерческого магазина; зависимые компоненты остаются под своими лицензиями.

## Переход alpha.4 → alpha.5

`0051_surveys` добавляет опросы и ответы. Существующие балансы не изменяются миграцией. Support Pro остаётся на `0005`. Downgrade запрещён после появления ответов; используйте согласованный backup. [Условия и проверка модуля](WORKSPACE_SURVEYS.md).

## Из alpha.6 в alpha.7

Миграция `0053_admin_passkeys` добавляет nullable уникальный `admin_users.passkey_user_handle` и таблицу временных challenges. Существующие пользователи, деньги и подписки сохраняются. Для регистрации включите `WEBAUTHN_ORIGIN` по [инструкции](ADMIN_PASSKEYS.md). Downgrade запрещён при зарегистрированных ключах; сначала удалите их контролируемо или примените исправление вперёд. Метрики и Grafana не требуют новой миграции. Обновление mobile workflow не генерирует ключи подписи владельца.

## Переход v21.0.0 → v21.0.1

Новый head — `0054_referral_levels`: снимки реферальных условий, дополнительные уровни и связь с журналом. Support Pro остаётся на `0005`. Перед обновлением выполните [согласованный CLI backup](BACKUP_CURRENT.md) двух баз и файлов. Исторические intents сохраняют прежний одноуровневый контракт; новые используют [программу уровней](REFERRALS_CURRENT.md). После появления новых финансовых строк downgrade запрещён.

CLI `.vpb` отличается от административного `.enc`; проверяйте копию по её регламенту. Старые updater/rollback не делают согласованный откат Support Pro. Для эксплуатации восстановление сначала проверяется на изолированном сервере.

## Переход v21.0.1 → v21.1.0

Новый head `0057_partner_commissions`, промежуточные 0055 customer passkeys и 0056 support topology. Support Pro остаётся на 0005. Перед обновлением создайте согласованный backup. Новые financial rows не начисляются задним числом, историю нельзя удалить downgrade. У обновлённой установки задайте `CUSTOMER_WEBAUTHN_ORIGIN` вручную и пересоздайте backend/worker/bot; новая установка делает это автоматически. [Полный production-регламент](PRODUCTION_CURRENT.md).

## Обновление 21.1.0 → 21.2.0

После согласованного backup и стенда обновите исходники до `v21.2.0` по основному регламенту. Head магазина — `0058_customer_operations`, Support Pro — `0005`. Примените миграции до запуска новых backend/worker/бота; затем пересоберите админку/кабинет/Mini App. Новая миграция добавляет encrypted preview, постоянные связи и batch-журнал, не импортирует автоматически клиентов или деньги.

Проверьте новый административный раздел и [регламент импорта](CUSTOMER_OPERATIONS_CURRENT.md). После импортных связей/batch-журнала downgrade 0058 запрещён. Для возврата к согласованной копии остановите запись, сверяйте новые операции и используйте штатный restore. Production gate и остальные незавершённые строки матрицы не меняют статус от одного обновления.
