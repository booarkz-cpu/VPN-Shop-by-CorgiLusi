# VPN Shop 20.0.22: установка с нуля на VDS

Актуальный маршрут для релиза v20.0.22. Проверяйте итог успешного CI и заметки выпуска перед установкой.

Эта инструкция рассчитана на владельца нового сервера Ubuntu/Debian. Команды вводятся в терминале сервера; строки вида `example.com` заменяются вашими доменами. В результате запустятся магазин, бот, админка, кабинет и Support Pro с HTTPS. **Приём реальных платежей останется закрытым** до отдельного успешного staging E2E v2 и включения допуска по [регламенту платежей](../../README.md). Установка сервера сама по себе этот допуск не открывает.

## Если установка v20.0.21 остановилась на `SUPPORT_REDIS_PASSWORD`

Ошибка происходит после копирования файлов и создания `/opt/vpn-shop/.env`, до настройки firewall и запуска контейнеров. Секреты в `.env` уже записаны. Не удаляйте эту папку и не публикуйте содержимое `.env`.

Сохраните неполную установку переименованием, затем получите исправленный тег и повторите установку. Выполняйте команды из SSH на том же VDS:

```bash
sudo test -f /opt/vpn-shop/.env && \
sudo test -d /opt/vpn-shop-src/.git && \
sudo mv /opt/vpn-shop "/opt/vpn-shop-incomplete-$(date -u +%Y%m%dT%H%M%SZ)" && \
sudo git -C /opt/vpn-shop-src fetch --tags origin && \
sudo git -C /opt/vpn-shop-src checkout v20.0.22 && \
cd /opt/vpn-shop-src && \
sudo bash deploy/install-vps.sh
```

Если первая проверка не удалась, остановитесь: эти команды рассчитаны на стандартные пути `/opt/vpn-shop` и `/opt/vpn-shop-src`. Повторно введите параметры установки; при случайном пароле администратора будет создан новый пароль. Не копируйте старый `.env` в новую установку. Сохранённую папку с секретами удаляйте только после успешного запуска и переноса нужных сведений в защищённое хранилище.

## 0. Подготовьте доступ и данные

Нужны VDS с Ubuntu 24.04 LTS или Debian 12, доступ администратора по SSH, публичный IPv4, минимум 2 vCPU / 4 ГБ RAM / 30 ГБ свободного диска (больше при реальных нагрузках), собственный домен, токен бота от [@BotFather](https://t.me/BotFather), URL и API-токен уже работающей панели Remnawave. Для TLS внешний firewall провайдера должен пропускать TCP 80 и 443; UDP 443 нужен для HTTP/3. SSH оставьте открытым на фактическом порту. Не используйте VDS, на котором уже работает другой веб-сервер на 80/443.

Запишите названия пяти отдельных DNS-имён, например:

| Назначение | Пример |
| --- | --- |
| API | `api.vpn.example.com` |
| Админка | `admin.vpn.example.com` |
| Telegram Mini App | `app.vpn.example.com` |
| Кабинет покупателя | `cabinet.vpn.example.com` |
| Обращения Support Pro | `support.vpn.example.com` |

В панели регистратора добавьте для каждого имени запись **A** с публичным IPv4 вашего VDS. Если у сервера нет IPv6, удалите старые **AAAA**, иначе браузер может пытаться попасть на чужой адрес. Дождитесь обновления DNS. Webhook маршруты опубликованы на API-домене; установщик устанавливает `WEBHOOK_BASE_URL` равным адресу API. Точный callback и поддержку платёжного провайдера проверьте в staging до живых списаний.

Сохраните вне сервера безопасную копию: токена Remnawave, токена BotFather, доступа к панели домена и учётных данных хостера. Не отправляйте их в чат или issue GitHub.

## 1. Подключитесь через SSH

В Termius создайте **New Host**: Address = IPv4 сервера, Port = порт SSH (обычно `22`), Username = выданный хостером `root` или другой sudo-пользователь. Для Windows подойдёт и PowerShell:

```powershell
ssh root@203.0.113.10
```

Для macOS/Linux команда та же в Terminal. При первом подключении сверяйте fingerprint ключа с данными хостера; запрос пароля в терминале не показывает набранные символы. Если входите не как root, добавляйте `sudo` к серверным командам. Оставьте вторую SSH-сессию открытой на время проверки firewall.

Проверьте систему и ресурсы:

```bash
cat /etc/os-release
free -h
df -h /
ss -ltnp | grep -E ':(80|443) ' || true
```

Последняя команда должна быть пустой на новом сервере. Если заняты 80/443, разберитесь с существующим сервисом до установки; не останавливайте чужой проект вслепую.

## 2. Проверьте DNS с сервера

Подставьте свой домен вместо `vpn.example.com`:

```bash
sudo apt-get update
sudo apt-get install -y dnsutils curl git ca-certificates
for name in api admin app cabinet support; do dig +short A "${name}.vpn.example.com"; done
```

Все пять ответов должны совпадать с IP VDS. Проверьте в панели хостера внешний firewall для TCP 80/443, UDP 443 и вашего SSH-порта. Установщик настроит также локальный UFW; если SSH работает на нестандартном порту, он берёт порт текущей SSH-сессии и открывает его до включения UFW. На сервере с несколькими портами SSH заранее откройте дополнительные порты вручную.

## 3. Скачайте проверенную версию

После публикации релиза используйте его тег, а не меняющуюся ветку `main`:

```bash
cd /opt
sudo git clone --branch v20.0.22 --depth 1 https://github.com/booarkz-cpu/shop-by-boo.git vpn-shop-src
cd /opt/vpn-shop-src
git rev-parse --short HEAD
```

Проверьте, что открыли официальный репозиторий и тег. **Не запускайте** в этой папке `docker compose up` до создания секретов: образец `.env.example` содержит заглушки. Установщик предложит параметры и сам создаст `/opt/vpn-shop/.env` и `/opt/vpn-shop/support-pro/.env`.

## 4. Запустите установщик

```bash
cd /opt/vpn-shop-src
sudo bash deploy/install-vps.sh
```

На вопросы ответьте доменами из таблицы, email администратора, паролем (или Enter для случайного), бот-токеном, именем бота без `@`, URL и токеном Remnawave. Секретные поля на экране не отображаются. Выберите `none` для платёжного провайдера, если ещё нет тестового контура и согласованных настроек. Остальные параметры можно оставить по умолчанию только после прочтения подсказки. `PAYMENTS_SANDBOX=true` для production запрещён. При неудачной проверке имени домена установка останавливается **до** изменений firewall.

Первый запуск устанавливает Docker, закрепляет digests базовых образов, собирает интерфейсы и запускает сервисы. Это может занять десятки минут. Не прерывайте SSH во время сборки. Если соединение нестабильно, заранее откройте `tmux`:

```bash
sudo apt-get install -y tmux
tmux new -s vpn-install
sudo bash /opt/vpn-shop-src/deploy/install-vps.sh
```

Вернуться к сеансу после переподключения: `tmux attach -t vpn-install`. Установщик не перезаписывает существующую `/opt/vpn-shop`; для неё используйте раздел обновления. При запуске через `curl | bash` также нужен настоящий SSH-терминал для вопросов, но фиксированный git-тег удобнее проверять.

**Сразу запишите** показанный один раз пароль админки, отдельный пароль Support Pro и его TOTP seed/QR URI в менеджер паролей. Не снимайте скриншоты с токенами и не публикуйте вывод установщика. Если установка оборвалась после создания `/opt/vpn-shop`, изучите ошибку, не удаляйте каталог с секретами и резервными копиями.

## 5. Проверьте контейнеры и HTTPS

```bash
cd /opt/vpn-shop
sudo docker compose --env-file .env config --quiet
sudo docker compose ps
curl -fsS https://api.vpn.example.com/health/ready
curl -I https://admin.vpn.example.com/
curl -I https://app.vpn.example.com/
curl -I https://cabinet.vpn.example.com/
curl -I https://support.vpn.example.com/
```

Первые три команды выполняются в каталоге установки, а имена в `curl` замените на свои. `/health/ready` должен ответить `"ok": true`; он возвращает 503 при недоступной БД или Redis. TLS-сертификат браузер должен принимать без предупреждения. На первом старте выпуск сертификата Caddy может занять несколько минут. Проверка конфигурации с `--quiet` не печатает секреты в терминал.

Если что-то не работает:

```bash
cd /opt/vpn-shop
sudo docker compose ps
sudo docker compose logs --tail=100 backend worker bot caddy support_pro support_migrate
sudo docker compose exec -T backend alembic current
sudo ufw status numbered
```

Не вставляйте в открытые тикеты целые `.env`, `docker compose config` без `--quiet`, webhook URL или логи с личными данными. Проверьте A/AAAA, открытые TCP 80/443, наличие свободного диска и правильность доменов. При уже созданной базе смена `DB_PASSWORD` в `.env` сама по себе **не меняет** пароль PostgreSQL; ротацию проводите отдельно и согласованно.

## 6. Первый вход и функции

Откройте `https://admin.vpn.example.com`, войдите email/паролем установки, включите TOTP и сохраните recovery-коды. Создайте вторую MFA-учётную запись администратора для операций восстановления. Пароль в `.env` используется только при первом bootstrap и не сбрасывает существующую учётную запись. В Support Pro войдите отдельными данными и TOTP из вывода установщика; пароль магазина там не подходит.

Напишите боту `/start`. В @BotFather назначьте Mini App URL `https://app.vpn.example.com`. Проверьте открытие Mini App внутри Telegram и в браузере, вход в кабинет, отображение тарифов и подключение к Remnawave без покупки. Создайте тестовый тариф, но не включайте живые платежи. Пользовательские VPN-подписки зависят от внешней панели Remnawave; клиентам нужен поддерживаемый VPN-клиент.

Провайдеру платежей задавайте callback только после проверки его подписи, точного URL и сетевого доступа на отдельном staging. Даже заполненные ключи в `.env` не означают, что реальное списание безопасно включать. Полный путь: создание платежа → callback → запись paid → выдача → повтор callback → возврат → отзыв доступа → сверка; каждую кассу проверяйте отдельно. Для подготовки второго VDS и границ текущей версии используйте [пошаговую инструкцию staging](STAGING_VDS_E2E_OPERATOR_20_0_18.md); критерии будущего полного прогона приведены в [контракте staging E2E v2](STAGING_E2E_V2_IMPLEMENTATION.md).

## 7. Секреты и резервные копии

```bash
cd /opt/vpn-shop
sudo ls -l .env .env.images support-pro/.env
sudo docker compose ps
```

У секретных файлов должны быть права `-rw-------` и владелец root. Сохраните защищённую копию `.env`, `.env.images` и `support-pro/.env` **вне VDS**: потеря `APP_SECRET` лишит доступа к уже зашифрованным настройкам. Также нужны ключи Android/Apple, если вы подписываете приложения. Не копируйте эти файлы в репозиторий.

Для рабочей базы настройте расписание, шифрование, срок хранения и off-site расположение в **Admin → Бекапы**. `scripts/backup.sh` только показывает контейнеры, он не создаёт dump. Проведите пробное восстановление на отдельном стенде и запишите дату последнего успешного восстановления. Контроль: размер файлов, проверка архива, `pg_restore`/`psql` на чистой базе, вход в админку и пробная выдача в staging. Автоматический снимок перед обновлением хранится локально в `/opt/vpn-shop/.rollback` и не заменяет off-site backup.

## 8. Обновление существующей установки

Перед работой сохраните off-site backup и проверьте свободное место. Обновление получает ZIP последнего релиза и его SHA-256, создаёт локальный снимок и дамп БД, затем запускает сборку:

```bash
cd /opt/vpn-shop
sudo bash scripts/update-from-github.sh
sudo bash scripts/doctor.sh
curl -fsS https://api.vpn.example.com/health/ready
```

При ошибке дампа обновление отменяется до копирования кода. При ошибке сборки скрипт пытается восстановить исходники и БД из снимков; секреты сохраняет на диске. Если восстановление не завершилось, остановите продажи и не запускайте поверх повреждённого состояния ещё одно обновление. Проверьте `/opt/vpn-shop/.rollback/RECOVERY_MODE`, последний dump, журнал и восстановите на отдельном стенде или с помощью администратора БД. Каталог `.rollback` содержит чувствительный дамп, ограничьте к нему доступ и переносите только по защищённому каналу.

Для обновления с 20.0.15 сначала вручную создайте недостающий `support-pro/.env`, если его нет, и согласуйте секреты Support Pro с основной `.env`; не заменяйте существующий `SESSION_SECRET` без плана завершения сеансов. Пример структуры — `support-pro/.env.example`. Запуск нового установщика поверх существующего каталога не требуется.

## 9. Операционная проверка

Раз в день смотрите `sudo docker compose ps`, `/health/ready`, заполнение диска, срок TLS-сертификатов, свежесть backup, ошибки очереди и Support Pro. После каждой смены домена, кассы, доступа Remnawave или ключей повторяйте проверки. При серьёзном сбое выключите приём платежей штатным gate, сохраните внутренние ID операций и проведите финансовую сверку. Не повторяйте списание только из-за отсутствия webhook или выдачи.

**Границы выпуска:** инструкция и тесты проверяют путь установки, но фактическое развёртывание на вашем VDS, DNS, кассы, Remnawave и реальные мобильные устройства требуют вашей отдельной проверки. Production APK/IPA публикуются только с ключами подписи владельца и отдельной проверкой workflow.
# Сохранение конфигурации при откате

Перед обновлением и откатом сохраните вне сервера резервные копии базы данных и локальных файлов `.env` и `.env.*` каждого компонента. Скрипты `scripts/update.sh` и `scripts/rollback.sh` переносят обычные вложенные файлы окружения из установленного дерева в восстановленную версию. После восстановления проверьте значения конфигурации и доступность сервисов через `./scripts/doctor.sh`. Не помещайте секреты в архив исходников или Git.
