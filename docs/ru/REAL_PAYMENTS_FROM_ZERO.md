# Реальные платежи: подробная инструкция с нуля

**Впервые настраиваете ЮKassa?** Откройте [инструкцию с названиями каждой кнопки и поля](YOOKASSA_CLICKS_BEGINNER.md).

**Проверено по исходникам `main` (14cf68e), 28.09.2026; выпущенный тег — `v20.0.18`.** Это руководство для владельца магазина, который ещё не настраивал кассу. Примеры доменов и IP заменяйте своими. Оно не является подтверждением, что ваш сервер или конкретная касса готовы к работе.

> **Главное ограничение текущей версии.** На `v20.0.18` штатно принимать реальные платежи нельзя. Встроенная проверка всегда выдаёт `contract_version=1`, `full_e2e=false`, а допуск требует `contract_version=2`, `full_e2e=true`, `status=passed` по текущей конфигурации не старше 24 часов. Включение через админку/API вернёт 409. Даже на staging внешний пользовательский checkout пока блокируется тем же gate (503). Шаги 1–5 можно подготовить сейчас; шаги 6–9 выполняйте **только после выпуска с реально реализованным E2E v2 и его успешной проверки**. Не редактируйте статус в БД и не убирайте проверку в коде.

## Слова без технического жаргона

- **Production** — рабочий магазин; списываются настоящие деньги покупателей.
- **Staging** — отдельный тестовый магазин, сервер, база, бот и Remnawave. Касса здесь использует тестовые ключи.
- **Касса/провайдер** — YooKassa, Platega, RollyPay, Stripe, PayPal и т. п. Начните с **одной** поддерживаемой в вашем регионе и договоре кассы, не включайте их все сразу.
- **Webhook** — HTTPS-запрос от кассы к вашему API, например «платёж завершён». Перенаправление браузера покупателя обратно на сайт **не** подтверждает списание.
- **Gate** — серверный допуск новых реальных списаний. Он не заменяет настройки ключей, проверку webhook или выдачу VPN.
- **Возврат** — отдельная финансовая операция; её успешность и отзыв VPN-доступа проверяют отдельно.

## 1. Подготовьте два независимых контура

1. Нужны два VDS (рекомендуемый для инструкции v20.0.18 минимум на каждый: 2 vCPU, 4 ГБ RAM, 30 ГБ свободного места), SSH-доступ, отдельные DNS-имена, отдельные бот-токены и две панели/организации Remnawave. Production и staging не должны делить базу, Redis, панель VPN и платёжные ключи.
2. Например, для production создайте A-записи `api.vpn.example.com`, `admin.vpn.example.com`, `app.vpn.example.com`, `cabinet.vpn.example.com`, `support.vpn.example.com` на IP первого VDS. Для staging используйте такие же имена в зоне `stage.vpn.example.com` на IP второго VDS. Если IPv6 не настроен, удалите неверные AAAA-записи. Откройте TCP 80/443 и SSH в firewall хостера; локальный firewall настроит установщик.
3. Создайте отдельную учётную запись и **тестовый магазин** у выбранной кассы. Уточните у неё доступные методы оплаты, тестовый возврат, уведомления, валюту, параметры чеков и условия рабочего магазина. Например, YooKassa документирует отдельные ключи тестового магазина и тестовые платёжные данные: [официальная инструкция](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing). Конкретные требования к договору и чекам согласуйте с кассой и вашим специалистом по учёту.
4. Подготовьте менеджер паролей и внешнюю защищённую копию конфигурации и базы. Не отправляйте `.env`, секреты, данные карты, полные ссылки оплаты и дампы в GitHub, чат или общедоступный тикет.

**Проверка перед следующим шагом:** DNS каждого имени указывает на свой VDS; у staging ключи и панель VPN не совпадают с production.

## 2. Поставьте production, оставив кассы выключенными

Следуйте [подробной установке v20.0.18](VDS_PRODUCTION_20_0_18.md), особенно шагам про DNS, секреты, SSL, резервные копии и первый вход. На вопрос о платёжном провайдере ответьте `none`. Команды ниже выполняются **на production VDS**:

```bash
cd /opt
sudo git clone --branch v20.0.18 --depth 1 https://github.com/booarkz-cpu/shop-by-boo.git vpn-shop-src
cd /opt/vpn-shop-src
sudo bash deploy/install-vps.sh
```

После установки проверьте:

```bash
cd /opt/vpn-shop
sudo docker compose --env-file .env config --quiet
sudo docker compose ps
curl -fsS https://api.vpn.example.com/health/ready
```

Админка: `https://admin.vpn.example.com`. Войдите, включите TOTP, сохраните recovery-коды вне сервера и создайте вторую MFA-учётную запись администратора для восстановления. Настройте отдельное резервное копирование и **пробное восстановление** на чистом стенде. Не считайте наличие файла backup доказательством восстановления.

В production конфигурация должна иметь `APP_ENV=production`, `PAYMENTS_SANDBOX=false`, `COOKIE_SECURE=true`. Не публикуйте весь файл и не выполняйте `docker compose config` без `--quiet`: команда может напечатать секреты. На этом этапе отказ новым внешним платежам — правильный результат.

## 3. Поставьте staging на втором сервере

Повторите установку из шага 2 **на staging VDS** с его доменами, ботом и Remnawave. Текущий установщик создаёт `APP_ENV=production`; сначала завершите установку, затем **только на staging** отредактируйте `/opt/vpn-shop/.env`:

```bash
cd /opt/vpn-shop
sudoedit .env
```

Установите `APP_ENV=staging` и `PAYMENTS_SANDBOX=true`. Используйте только тестовые ключи кассы. Сохраните файл и проверьте запуск:

```bash
sudo docker compose --env-file .env config --quiet
sudo docker compose up -d --build
sudo docker compose ps
curl -fsS https://api.stage.vpn.example.com/health/ready
```

Создайте тестового покупателя и недорогой тестовый тариф. Проверьте вход, Mini App, связь с **тестовой** Remnawave и резервное восстановление. Внутренний `sandbox://` подходит для проверки магазина без реальной кассы, но не является E2E внешнего провайдера.

## 4. Зарегистрируйте webhook у одной кассы

В официальном кабинете **тестового** магазина задайте публичный HTTPS URL staging. Не вводите callback на `localhost` и не используйте production ключ для staging. Точные события и способ проверки подлинности определяются провайдером; сверяйте их с его текущей документацией.

| Касса | Webhook на вашем staging API | Главное при проверке |
| --- | --- | --- |
| YooKassa | `https://api.stage.vpn.example.com/api/webhooks/yookassa` | IP источника по актуальному списку и повторная проверка объекта через API кассы |
| Platega | `https://api.stage.vpn.example.com/api/webhooks/platega` | Заголовки подписи, сумма, валюта, ID заказа; подтверждённый тестовый возврат |
| RollyPay | `https://api.stage.vpn.example.com/api/webhooks/rollypay` | Подпись, время, сумма, валюта; уточните доступность возврата в sandbox |
| Stripe | `https://api.stage.vpn.example.com/api/payments/webhooks/stripe` | Секрет **именно этого endpoint**, подпись сырого тела, оплаченная сессия/intent |
| PayPal | `https://api.stage.vpn.example.com/api/payments/webhooks/paypal` | Sandbox webhook ID и проверка подписи через API PayPal |
| Crypto | `https://api.stage.vpn.example.com/api/webhooks/crypto` | Ключ/подпись шлюза и подтверждение статуса через его API |

Для YooKassa в «Интеграция → HTTP-уведомления» укажите URL и нужные события `payment.succeeded`, `payment.canceled`, `refund.succeeded`; официальный раздел [«Входящие уведомления»](https://yookassa.ru/developers/using-api/webhooks) описывает настройку и требования к HTTPS. Для Stripe см. [проверку webhook](https://docs.stripe.com/webhooks) и [проверку подписи](https://docs.stripe.com/webhooks/signature), для PayPal — [проверку подписи](https://developer.paypal.com/api/webhooks/v1/verify-webhook-signature-post/) и [повторную доставку событий](https://developer.paypal.com/api/rest/webhooks/events-dashboard/). Сам факт доставки HTTP 200 не доказывает, что магазин правильно выдал подписку.

**Текущий стоп:** внешний `POST /api/payments/create` на staging v20.0.18 возвращает 503 до прохождения gate. Одна только настройка URL не позволит выполнить полную покупку; не заменяйте реальный webhook ручным вызовом ради «зелёного» результата.

## 5. Подготовьте настройку проверки в админке

В **production-админке** заполните staging E2E: адрес staging API, адрес и токен staging Remnawave, staging-покупателя/тариф, **тестовые** ключи выбранной кассы и необходимые адреса возврата из её документации. Эта запись хранится в production базе; после изменения конфигурации revision меняется и старый допуск закрывается. Для Platega/RollyPay нельзя выдумывать URL возврата, чтобы заполнить форму.

Текущий runner v1 может проверить отдельные ответы API и выдать `[PASS]` на промежуточных этапах, но итог остаётся `contract_version=1`, `full_e2e=false`. Он **не подтверждает** всю цепочку: обычный checkout → подписанный webhook → оплата → выдача → повтор webhook → возврат → отзыв доступа. Не нажимайте «Разрешить реальные платежи» в надежде, что тест v1 откроет продажи.

### Чего ждать от следующего выпуска

Разработчик должен выпустить runner v2, который действительно запускает обычную покупку через staging, связывает доказательства с одним order ID, автоматически сверяет webhook, выдачу, повтор и возврат, отказывает при пропуске любого этапа и выдаёт `status=passed`, `contract_version=2`, `full_e2e=true` только после полного прохождения. Само изменение номера версии или ручная запись этих полей не является проверкой. Перед установкой следующего релиза сравните его changelog и код с [контрактом E2E v2](STAGING_E2E_V2_IMPLEMENTATION.md) и дождитесь успешного CI.

## 6. После появления настоящего v2: пройдите staging целиком

Для **каждой** планируемой кассы повторите весь маршрут с новой тестовой покупкой:

1. Создайте покупку обычным способом из staging кабинета/Mini App. Запишите внутренний ID, `order_id`, тариф, сумму, валюту и ID на стороне кассы. Повторите запрос с тем же ключом идемпотентности: должен остаться **один** заказ и **один** provider intent.
2. Оплатите на официальной тестовой странице провайдера. Не считайте браузерный редирект свидетельством оплаты. Сверьте событие в кабинете кассы, его доставку на staging и серверную проверку подписи/объекта; сумма, валюта и order ID должны совпасть.
3. Дождитесь `paid` и `fulfillment_status=completed`; найдите ровно одну подписку и один VPN-доступ в staging Remnawave. Проверьте срок и ограничения тарифа. Ошибка Remnawave должна приводить к контролируемому повтору без второй выдачи.
4. Повторно доставьте **то же подписанное событие** штатным механизмом кассы. Убедитесь, что не появились второй заказ, списание, финансовая запись или VPN-доступ. В отдельном отрицательном тесте неверная подпись/сумма/валюта/чужой order ID не меняют состояние.
5. Сделайте полный тестовый возврат через **штатную кнопку магазина**, а не через прямую правку БД. Проверьте подтверждённый refund ID/статус у кассы, запись в финансовом журнале, отзыв нужного доступа в Remnawave. Повторная команда возврата не должна списать деньги дважды; поздний success webhook не должен восстановить подписку.
6. Проверьте итог на сервере: `status=passed`, `contract_version=2`, `full_e2e=true`, текущая revision, время завершения не старше 24 часов, тот же commit/tag и **та же касса**. Сохраните обезличенный протокол проверки. Если касса не позволяет проверить тестовый refund, она не прошла этот регламент.

При расхождении ID, сумм, доступа или статуса **не создавайте повторную оплату наугад**: сначала запросите состояние платежа у провайдера и сверьте локальный заказ. Встроенный v1 не может выполнить эти шаги до выпуска исправления.

## 7. После PASS: подготовьте production ключи

На production используйте **рабочий** merchant/account и отдельные рабочие ключи, не тестовые. Подключите только прошедшую проверку кассу. В `/opt/vpn-shop/.env` проверьте `APP_ENV=production`, `PAYMENTS_SANDBOX=false`, `COOKIE_SECURE=true`, `DEFAULT_CURRENCY` и `WEBHOOK_BASE_URL=https://api.vpn.example.com`. Для YooKassa нужны рабочие `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY` и актуальный `YOOKASSA_WEBHOOK_IP_ALLOWLIST`; для Stripe — `STRIPE_SECRET_KEY`/`STRIPE_WEBHOOK_SECRET`, для PayPal — `PAYPAL_CLIENT_ID`/`PAYPAL_CLIENT_SECRET`/`PAYPAL_WEBHOOK_ID`. Другие кассы имеют свои поля в `.env.example`. Не копируйте staging `.env` на production.

В кабинете **рабочей** кассы создайте webhook уже для `https://api.vpn.example.com/...` с тем же путём из таблицы и реальными событиями. Для PayPal и Stripe секрет/ID webhook разных сред различается. Проверьте доставку и SSL. После изменений конфигурации выполните `sudo docker compose --env-file .env config --quiet`, перезапустите требуемые сервисы по инструкции релиза и снова проверьте `/health/ready`. Храните конфигурацию с правами только для владельца. Изменение ключей или staging-настроек требует повторной проверки допуска.

**Ограничение:** описанные действия не открывают оплату на v20.0.18. Нужен выпущенный v2, успешно завершённый staging-прогон и действительный результат в production базе.

## 8. Включите gate и сделайте одну контрольную реальную оплату

Только после всех проверок из шага 6 уполномоченный администратор с MFA в production админке открывает «Безопасность / Платежи» и нажимает «Разрешить реальные платежи». API `POST /api/admin/payments/production-gate` с `enabled=true` сам повторно проверяет полный PASS, revision и возраст. Ответ 409 означает **остановиться**, а не редактировать БД или отключать проверку. Убедитесь в панели, что допуск включён.

Создайте **один** контрольный заказ на минимальную разрешённую вашим договором сумму обычной рабочей платёжной страницей. Это уже настоящее списание. Сверьте выписку/кабинет кассы, webhook, один локальный `Payment`, один VPN-доступ, чек и сумму по журналу. Затем оформите возврат штатной процедурой и подтвердите его на стороне кассы и в магазине. Только после успешного контроля открывайте покупку другим клиентам. Если провайдер, сумма, тариф или идентификатор расходятся, сразу остановите новые платежи.

## 9. Следите за работой каждый день

Проверяйте контейнеры (`sudo docker compose ps`), `https://api.vpn.example.com/health/ready`, доставку webhook у кассы, незавершённые заказы и возвраты, очередь выдачи, доступность Remnawave, состояние gate, резервные копии и свободное место. Gate должен закрыться при устаревании результата старше 24 часов или смене staging revision; проверьте это до живого запуска.

При инциденте в админке нажмите «Заблокировать реальные платежи» (`enabled=false`), сохраните обезличенные order/provider/refund ID и UTC-время, затем сверьте транзакции с кассой. Не делайте повторное списание и не правьте статусы вручную. Если backend вернул 503, сначала различите отсутствие допуска, maintenance mode, выключенную функцию платежей и недоступность кассы. Логи читайте на нужном VDS: `sudo docker compose logs --tail=100 backend worker caddy`; перед передачей удалите из них секреты и личные данные.

## Быстрая проверка «можно открывать?»

| Вопрос | Если ответ «нет» |
| --- | --- |
| Есть релиз с реальным runner E2E v2 и успешным CI? | Не включать |
| Production и staging физически разделены, а ключи не совпадают? | Не включать |
| Каждая включаемая касса прошла checkout, подписанный webhook, выдачу, повтор, refund и отзыв? | Не включать эту кассу |
| Сервер сам сохранил полный PASS v2 по текущей revision младше 24 часов? | Не включать |
| Восстановление копии, MFA, TLS и мониторинг проверены? | Не включать |
| Контрольный реальный заказ и возврат совпали у кассы, магазина и Remnawave? | Не открывать продажи покупателям |

См. также [краткий маршрут](steps/04-payments.md), [инструкцию оператора staging v20.0.18](STAGING_VDS_E2E_OPERATOR_20_0_18.md) и [полный регламент для новичка](PAYMENTS_VDS_BEGINNER_2026_09_28.md).
