# Staging E2E і допуск платежів — v20.0.8

## Межі поточної перевірки

Адмінпанель запускає `scripts/staging-e2e.sh` у backend. Скрипт перевіряє HTTPS health, доступність тестового Remnawave, створення платежу в пісочниці, статус, суму й валюту в провайдера, повторне читання та повернення коштів. Це **перевірка API провайдера**, а не повний наскрізний E2E. Скрипт не спостерігає вхідний webhook, стан замовлення після нього, видачу підписки в Remnawave, повторну доставку webhook чи стан після повернення. Тому він не може встановити `passed` і дозволити реальні платежі. Старі результати й прапор v20.0.7 втрачають чинність.

## Підготовка окремого стенда

1. Зробіть копію PostgreSQL, медіа та `.env`; перевірте відновлення на іншому вузлі. Не використовуйте бойові платіжні ключі.
2. Виділіть окремі HTTPS домени, PostgreSQL, Redis, Remnawave, тариф і користувача. Установіть `APP_ENV=staging`, `PAYMENTS_SANDBOX=true`, `COOKIE_SECURE=true`; використовуйте ключі пісочниці.
3. Згенеруйте окремі токени runner і користувача. В адмінпанелі вкажіть публічний URL API, тестовий Remnawave, тариф і провайдерів. Перевірте походження ключів.
4. Перевірте `docker compose config --quiet`, `docker compose ps`, `/health`, міграції, DNS і сертифікати. Не відкривайте зовні порти БД, Redis або runner.
5. Налаштуйте справжні підписані webhook кожного провайдера на окрему адресу staging. Збережіть ID замовлення, платежу та події без секретів.

## Матриця повного ручного E2E

Повторіть для кожного провайдера; записуйте час, ID, очікуваний і фактичний стан. Не публікуйте токени чи платіжні дані.

| Крок | Дія | Критерій успіху |
| --- | --- | --- |
| 1 | Створити замовлення в інтерфейсі й відкрити checkout | Одне замовлення, правильні тариф, сума й валюта, HTTPS посилання пісочниці |
| 2 | Завершити тестову оплату | Провайдер підтверджує той самий ID і суму; невідповідність відхиляється |
| 3 | Дочекатися справжнього підписаного webhook | Подію застосовано один раз, замовлення оплачене; опитування статусу не замінює webhook |
| 4 | Перевірити видачу | Створено рівно один доступ Remnawave; покупець бачить робоче посилання й строк дії |
| 5 | Повторити webhook і перевірку статусу | Немає другої оплати, замовлення чи доступу |
| 6 | Надіслати неправильний підпис і невідповідні дані | Запит відхилено, фінансовий стан і підписка незмінні |
| 7 | Зробити повне повернення в пісочниці | Провайдер і магазин підтверджують повернення; замовлення не лишається помилково оплаченим |
| 8 | Тимчасово вимкнути Remnawave | Контрольована повторна спроба без дублювання видачі |

Окремо перевірте скасування checkout, завершення строку, одночасні запити, затриманий webhook, перезапуск backend/worker та відновлення з резервної копії. Відповідь API `verify` не є доказом доставки webhook.

## Автоматична перевірка й результат

Збережіть конфігурацію staging в адмінпанелі та запустіть перевірку. Відкрийте кожне `[CHECKOUT]` з журналу і завершіть оплату в пісочниці. Після перевірок провайдера й повернення скрипт повідомляє `[INCOMPLETE]`; це очікувано і **не дозволяє** production. `failed` означає, що не пройшла навіть наявна частина. Для допуску потрібен новий контракт v2 із доказом webhook, видачі та ідемпотентності. Не змінюйте `payments.production_gate.v20_0_8` вручну в БД.

## Production та відкат

Перевірте аудит, моніторинг webhook і черг, відновлені копії, секрети й HTTPS. Доки повний E2E v2 не реалізовано, адмінпанель має відмовляти у ввімкненні реальних платежів. Новий ключ закриває старий допуск v20.0.7; уже прийняті замовлення треба звірити окремо. Під час інциденту призупиніть нові платежі, збережіть журнал і ID, звірте стан у провайдера та БД і виконуйте видачу або повернення лише через затверджену процедуру. Для відкату відновіть сумісні код і БД з перевіреної копії. Відкат на v20.0.7 повертає стару модель допуску й потребує ручного блокування платежів.
